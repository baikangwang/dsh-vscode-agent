## 一、目标 / 背景分析

### 1.1 用户诉求

用户在「DSH 配置」详情卡（`dsh.details` 视图）看到两处与实际不符的显示：

1. **「当前」通道显示「未知」**。用户明确知道当前这个由外部命令启动的 dsh 实例跑的是 `next` 通道，插件却显示 `未知`。
2. **括号提示与事实对不上**。括号写「（已选「latest」，待重启生效）」。这句话读起来是「配置选的是 latest、和实际运行的不一致、要重启才生效」。用户的预期里并没有「需要重启来切换通道」这件事，因此这条提示会误导用户去点「立即重启以生效」。

### 1.2 本轮要查清的问题

第一，`未知` 究竟是「插件真的没法知道」还是「插件本来能知道却没做」——这决定了它是设计取舍还是缺陷。

第二，括号提示在什么条件下才会渲染，它在用户这个场景下得到的结论为什么和用户认知对不上，以及这个结论本身与磁盘上的客观事实是否一致。

第三，修复后应该显示什么，怎样才能既把真实通道显示出来，又不回到 0.1.21 已经修掉的「假快照把待生效提示抹掉」那个失效形态。

### 1.3 为什么要修

通道是 dsh 版本来源的判定依据（`latest` / `next` / `alpha` 三个 npm dist-tag 指向不同版本线）。用户看到「未知」，就无法从面板判断「我这个实例到底跑在哪条线上」；看到一条与认知不符的待重启提示，就会去做一次没有意义的「重启以生效」动作。两件事叠加，面板在这一行上失去了可信度。

## 二、范围分析

### 2.1 本轮做什么

- 把「运行中 dsh 实例的真实启动通道」这套既有语义（0.1.21 改动点 5 建立）补全：在外部接管（external）场景下，用**只读**手段真实取回通道事实，而不是直接落 `未知`。
- 修正括号提示「（已选「X」，待重启生效）」的渲染判定，使它在「配置通道与运行通道一致」时不出现、在不一致时出现、在无法核实运行通道时不做出会误导人的断言。
- 给出完整的场景真值表、改动点清单、可无头自动验证的测试设计、风险与回归说明。

### 2.2 本轮不做什么

- 不改动 0.1.21 已经落定的核心语义「快照 channel 不回退配置值」。本轮是**延续并补全**该语义，不是推翻（理由见 §5.4）。
- 不新增创建进程、杀进程、重启进程的路径。本轮全部新逻辑只读。
- 不改变外部实例不代杀的红线（P0-D / ADR-2）。「立即重启以生效」在 external 场景仍然只给手动路径指引。
- 不改动通道切换的三分流决策函数 `resolveChannelRestartAction`，也不改动多窗口收敛、启动锁、死亡分支三分流等 0.1.21 / 0.1.22 已落定行为。
- 不理解析 dsh 服务自身的认证会话、不尝试从 401 响应体里提取版本或通道（该响应体不含此类事实，见 §四探针 5 排除项）。
- （v2 新增，QA-D23-02 / 03）**不读取 npx 缓存目录内的任何文件**：恢复链只消费命令行原文与运行时计算的哈希表，`channelProbe.ts` 零 `fs` 依赖、不触碰 `dshResolver.ts` 的模块内部边界（`npxRoot()` 保持不导出）。

## 三、现象与数据流溯源

### 3.1 「当前」通道这一行的完整数据流

这一行的字符串最终由 `channelSwitcherHtml` 拼出，值来自快照字段 `info.channel`。完整链路如下（行号为本轮实读的现状值；v2 按 QA-D23-13 更正第 ③ 步的文件归属）：

```
① 运行期事实的产生点
   src/runtime.ts:689   launchManaged 成功 → this.attachedChannel = this.options.channel
   src/runtime.ts:973   adopt 认领     → this.attachedChannel = adoptedRec?.channel ?? null
        └─ adoptedRec 的判定（同文件 971 行）= 记录存在 且 rec.pid === 被认领 pid
           不满足（例如 stale 记录描述的不是本进程）→ adoptedRec = null → 结果同为 null

② 快照组装
   src/runtime.ts:375    refreshLaunchInfo 把 channel: this.attachedChannel 交给 buildLaunchInfo
   src/launchInfo.ts:330 buildLaunchInfo 落盘 channel: input.channel ?? null

③ 面板渲染
   src/webviewDetails.ts:111  buildDetailsHtml(info, phase, {...})（唯一调用点）
   src/webviewHtml.ts:489     external 卡内 ${channelSwitcherHtml(info.channel, opts)} 调用点
   src/webviewHtml.ts:536     受管卡内   ${channelSwitcherHtml(info.channel, opts)} 调用点
   src/webviewHtml.ts:579     const pending = cfg !== null && cfg !== current
   src/webviewHtml.ts:580     const currentText = current ?? '未知'
   src/webviewHtml.ts:594     「当前」行渲染 <b>${escapeAttr(currentText)}</b>
```

结论：**「未知」不是某个渲染层的兜底文案，而是快照 `channel` 字段真的等于 `null`**；渲染层 `webviewHtml.ts:580` 只是把 `null` 如实写成「未知」。

### 3.2 external 路径下 `channel` 为什么是 `null`

沿 §3.1 第 ① 步的两个赋值点分别看：

- **首次发现式接管（step2 路径）**：`src/runtime.ts:563` 调用 `adopt(probePort, pid, 'external', probeKind?.kind ?? null, inst.dsh)`，第 5 个参数传的是**旧的注册表记录** `inst.dsh`。该记录要么是上一条 external 记录（本机实测为无 `channel` 字段，见 §四探针 1），要么 pid 与本次认领的 pid 不一致（本机实测：旧记录 pid=24540、本次认领 pid=21100，见 §四探针 2 的 runtime.log）。两种情况都让 `adoptedRec = null`，于是 `attachedChannel = null`。
- **注册表复用式接管（step1 路径）**：`src/runtime.ts:497` 同样把 `inst.dsh` 传进去，同理结果为 `null`。

再往上游看写入侧 `src/runtime.ts:1158`：

```ts
channel: keepDshStartedAt && prev !== null ? prev.channel : (this.attachedChannel ?? undefined),
```

external 认领时 `attachedChannel` 为 `null`，`undefined` 被 `JSON.stringify` 丢弃，**注册表里根本不写这个字段**。所以下一次接管时读到的记录里也没有 `channel`——这是一个自我延续的闭环：不写 → 读不到 → 显示未知 → 仍然不写。

### 3.3 这是哪次设计的决定、理由是什么

这是 **0.1.21 改动点 5** 的决定，出处三处（v2 按 QA-D23-09 更正引用）：

- 来源 1 §3.4 D-2 改动点 5 原文：「external 认领不写（插件无法确知外部进程真实通道，诚实缺省）」；
- 来源 1 §4.1 R-7（L360）原文：「如实呈现运行事实（插件无法确知外部进程真实通道）；待生效提示保持真、按钮可点；『更诚实、非回归』定性」；
- 来源 2 §2.2（L120）原文：「**不做**外部实例通道的自动探测（外部进程真实通道本插件无法确知，只做诚实标注）」；§3.3（L219）原文：「external 认领不写（插件无法确知外部进程真实通道，诚实缺省）」。

当时的驱动动因是**修复一个真实存在的失真**：0.1.21 之前快照 `channel` 是配置直通回显（旧代码 `channel: this.options.channel`），导致「用户改配置后重连 adopt 一个仍跑旧通道的实例」时，快照被刷成新值，「待生效」提示被悄悄抹掉，而进程实际还在跑旧通道。0.1.21 的修正方向——**快照只陈述运行实例的事实，不回退配置值**——是正确的，本轮完整沿用。

问题出在这条修正的一个**前提假设**上：「插件无法确知外部进程真实通道」。0.1.21 把「无法确知」当成既定事实（来源 2 L120 甚至把它写进了「不做什么」清单），于是用「落 null + 渲染未知」作为诚实降级。本轮实测证明这个前提**在本项目当前环境下不成立**（§四探针 2 / 3），因此「落 null」从「诚实的上策」退化成「放弃了可得事实的下策」。

### 3.4 「待重启生效」括号提示的确切生成位置与判定条件

生成位置在纯模块 `src/webviewHtml.ts` 的 `channelSwitcherHtml`（函数体 L577-598）：

```ts
// src/webviewHtml.ts:577-598（现状实读）
function channelSwitcherHtml(current: string | null, opts?: DetailsRenderOptions): string {
  const cfg = typeof opts?.configChannel === 'string' && opts.configChannel.length > 0 ? opts.configChannel : null
  const pending = cfg !== null && cfg !== current        // ← 待生效判定
  const currentText = current ?? '未知'
  ...
  const pendingNote = pending ? ` <span class="muted">（已选「${escapeAttr(cfg!)}」，待重启生效）</span>` : ''
  const pendingAction = pending ? `... <button class="primary" data-action="apply-channel-restart">立即重启以生效</button>` : ''
```

两个输入分别来自：

- `current` = 快照 `info.channel`（运行侧事实，§3.1 链路）；
- `cfg` = `configChannel` 渲染选项，由 `src/webviewDetails.ts:108-110` 现读 vscode 配置得到：

```ts
const cfgChannel = normalizeChannel(
  vscode.workspace.getConfiguration('dsh').get<string>('channel', 'latest'),
).channel
```

判定条件就是这一行：`cfg !== current`。它的语义是「将要生效的配置通道 ≠ 正在运行的通道」。这个判定本身没错，**它错在当 `current === null` 时的取值行为**：`cfg` 恒为非空字符串，`current` 为 `null`，于是 `cfg !== current` **恒为真**——不管配置通道和实际运行的通道是否真的相同。

这正是 0.1.21 有意写下的行为。来源 1 §3.4 改动点 5 的渲染层适配段原文：**「『待生效』判定在 current=null 时恒真——『已选 X，待重启生效』提示与『立即重启以生效』按钮保持渲染，不会被假快照抹掉」**。当时的设计意图是「宁可多提示，也不能漏提示」，因为在 0.1.21 的语境下漏提示（假快照抹掉提示）是已被证实的失效形态，而多提示的代价被判断为可接受。

### 3.5 用户这个场景下，括号提示与事实到底是什么关系

这一步需要把三条事实分别落定。本机实测（§四探针 1、2、3、4）结果如下：

| 事实 | 值 | 证据 |
|---|---|---|
| 配置通道 `dsh.channel` | `latest` | §四探针 1：`C:\Users\wangbaikang\AppData\Roaming\Code\User\settings.json` 中 `"dsh.channel": "latest"` |
| 运行实例真实启动通道 | `next` | §四探针 2 + 3：运行进程命令行指向 npx 缓存目录 `c8633a242642d858`，按 npm 的目录名算法反查该目录名等于 `@deepseek-ai/dsh@next` |
| 插件当前显示的结论 | 当前=未知、待重启生效=true | 用户截图 |

由此得出两点相互独立、必须分开处置的判断：

**判断 A（显示未知是缺陷）**：运行实例真实通道是 `next`，这是**当前环境实际可得的事实**（§四探针 3 完整走通了恢复链）。插件显示「未知」不是诚实降级，而是漏做。用户说的没错。

**判断 B（括号提示在逻辑上并不算错，但因为它依赖被漏掉的输入而变得误导）**：`cfg = latest`、`running = next`，两者确实不一致，因此 `pending = true` 在语义上**成立**。也就是说，用户当前磁盘上的配置通道确实是 `latest`，与实际运行的 `next` 不同；从「配置改了下一次启动才生效」这个既有契约看，提示并非凭空捏造。

用户感到「与事实不符」，真正的成因是：这一行同时缺了「运行侧那一半」（显示成未知），只留下「配置侧那一半」（latest）。用户看到的是一个**无法自洽的半句配置断言**——面板没说运行的是 `next`，所以用户无从判断「不一致」到底发生在哪里，只能读成一句没有依据的催促。一旦把运行通道如实补上（当前 `next`），这行就会自证其意：「当前 next（已选 latest，待重启生效）」。

因此本轮对判断 B 的处置是：**不否定 pending 判定本身，而是修掉「运行侧未知时也恒真渲染」这一条**。理由见 §5.3 的三条分支设计。

### 3.6 与截图另一处文案的关系：「npx 缓存存在 5 个版本（显示最新，未核实运行进程）」

这一行由 `src/launchInfo.ts:259-264` 的 `buildExternalVersionNote` 生成，处于**版本**语义域，与通道语义域正交，本轮不改。但要指出一个必然发生的副作用：本轮把运行通道恢复出来之后，同一张卡片上会出现「版本据 npx 缓存目录（未核实运行进程）」与「当前通道 next（据启动命令行）」并存的形态。二者**不矛盾**——版本仍是间接事实（缓存目录里有什么），通道是本次命令行直接证据——但读者容易混淆。为此本轮要求渲染层对通道值附来源标注（见 §5.1 / §5.3），使两者的证据强度差异在界面上可见。

### 5.2 runtime 侧接线

#### 5.2.1 恢复流程（v2 重写，QA-D23-04 / 11）

在 `src/runtime.ts` 的 `adopt()` 落点（现 L965-984 一带），**在 `refreshLaunchInfo`（L984）之前**执行以下判定序列：

**函数签名变更（方案 A，QA-D23-r2-01 选定修法）**：`adopt()`（现 L965，5 参）新增**可选**第 6 参：

```ts
// src/runtime.ts（设计稿）
private async adopt(
  port: number, pid: number | null, managedBy: ManagedBy, probeKind: ProbeKind | null,
  rec?: DshRecord | null,
  knownCommandLine?: string | null,   // 0.1.23 新增（可选，方案 A）：调用方本 tick/本步
                                      // 已取到的运行进程命令行原文（未截断）。仅当该 pid
                                      // 的命令行在认领前已被取过时才传；其余调用点不传。
): Promise<void>
```

`discoveryAdopt()`（现 L1346，5 参）同步新增**可选**第 6 参 `knownCommandLine?: string | null`，并透传给 `adopt`：

```ts
// src/runtime.ts（设计稿）
private async discoveryAdopt(
  port: number, pid: number | null, managedBy: ManagedBy, probeKind: ProbeKind,
  rec: DshRecord | null,
  knownCommandLine?: string | null,   // 0.1.23 新增（可选，方案 A）：透传给 adopt
): Promise<void> {
  this.beginAttachment()
  this.setState('starting')
  await this.adopt(port, pid, managedBy, probeKind, rec, knownCommandLine)
  await this.writeRegistry()
  this.startProbe()
}
```

判定序列（在 `adopt` 体内、`refreshLaunchInfo`（L984）之前）：

```
输入：rec（旧注册表记录，可 null）
     knownCommandLine（adopt 第 6 参，可 null/undefined：仅 discovery-port 传完整值）
     this.externalCommandLine（step2 路径已写入的 300 截断值，可 null）

第 1 步（跳过判据，QA-D23-11）：adoptedRec 存在且 adoptedRec.channel !== undefined
        → attachedChannel = adoptedRec.channel；attachedChannelSource = 'registry'
        → 零新增查询（注册表即缓存；同 pid 重复认领、跨窗口重连全部走此分支）
第 2 步（仅 external 且第 1 步未命中）：
        2a  复用优先顺序：
            (i)  knownCommandLine 非空（discovery-port 显式传参，方案 A）
                 → 直接喂 recoverChannelFromCmdline（零新增查询）
            (ii) 否则 this.externalCommandLine 非空（step2 字段复用）
                 → 直接喂 recoverChannelFromCmdline（零新增查询）
        2b  上述两者皆空 且 pid 非 null → 补一次 processCommandLine(pid, 15_000)
            （与 step2 L518 同函数同预算）
        2c  恢复成功 → attachedChannel = 恢复值；attachedChannelSource = 'cmdline'
            恢复失败 → attachedChannel = null；attachedChannelSource = null（诚实降级，rlog 留痕）
第 3 步（managed-own / extension 认领，rec 含 channel）：由第 1 步覆盖，source = 'registry'
第 4 步（launchManaged 成功，现 L689）：attachedChannel = options.channel；
        attachedChannelSource = 'launch-option'（QA-D23-07 补赋值落点）
```

要点说明：

- **复用优先、且复用媒介与 `beginAttachment()` 解耦（派单问题 5 的接法决定，v3 按 QA-D23-04 残留 / r2-01 修正）**：step2 路径下 `this.externalCommandLine`（`runtime.ts:522`，300 字符截断）在 `adopt` 调用前写入、调用时未被清空，2a-(ii) 成立，免掉第二次查询。**discovery-port 路径不再走该字段**：`discoveryAdopt` 首句 `beginAttachment()`（`runtime.ts:1347` → L452）会在 `adopt`（L1349）之前把 `this.externalCommandLine` 置 null（QA r2 动态对照探针实测：discovery-port 路径 adopt 入口读到 null，2a 永假）。v3 改为 `discoveryTick`（`runtime.ts:1306` 已取到完整 `cmdline`）经 `discoveryAdopt` 第 6 参**显式传完整值**给 `adopt`，2a-(i) 成立，同样零新增查询——复用与重置顺序彻底解耦，顺带消除「跨 tick 读到陈旧命令行」的隐患（QA 推荐方案 A）。
- **截断安全性**：step2 复用的是 300 截断值，探针 7 证实：本机命令行全长 130 字符，`_npx` 目录片段（含分隔符）位于下标 54–77，其中 16 位目录名位于 60–75，截断只会让 token 缺席（→ 2c 恢复失败 → 诚实降级），不会造出假值。discovery-port 传的是**未截断**的完整 `cmdline`，更无此虑。**决定：两条主路径均复用，不接受重复查询。**
- **新增查询只发生在「记录缺 channel 且调用方未传命令行且本窗口无字段」的认领路径**（step1 `runtime.ts:497`、step4 `runtime.ts:1206`、discovery-registry `runtime.ts:1291`）。这三条路径的上游都没有命令行查询（v2/v3 逐条实读确认），新增的是一条最长 15 s 的同步 `spawnSync`（`instance.ts:510-514`）。**step2 与 discovery-port 两条主路径均为新增查询 0**（v3 更正：v2 误把 discovery-port 写成「字段复用 0」，实际因重置顺序不可能复用，已改经显式传参实现 0）。
- **每个外部进程生命周期至多一次新增查询**：首次恢复成功后 `writeRegistry` 把 channel 写回注册表（§5.2.2），之后任何窗口（含本窗口）再认领同一 pid 都命中第 1 步，零查询。
- **向后兼容（探针 8 实证）**：`adopt(` 全调用点枚举为 5 处（L497 / L545 / L563 / L1206 / L1349），新增第 6 参为可选，**其余 4 处不传、行为不变**；仅 discovery-port 调用链（L1326 → L1349）传值。`discoveryAdopt(` 全调用点 2 处（L1291 discovery-registry / L1326 discovery-port），仅 L1326 传完整 `cmdline`，L1291 不传（discovery-registry 上游本无命令行查询，维持新增 1 次）。
- **退化子情形（v3.1 登记，QA-C23-03）**：discovery-port 的「新增查询 0」以「本 tick 已取到命令行」为前提。当 `discoveryTick` 本轮 `processCommandLine` 即返回 `null`（CIM 不可用降级）时，第 6 参为 `null`，`adopt` 落第 2b 步对同一 pid 再查一次，最坏再叠加 15 s 同步阻塞。代码忠实于本条 2b 回退规格，**本轮不做短路优化**（退化子情形；短路需先修订本节规格，属设计变更，成本高于收益）。详细口径见 §5.8 退化子情形说明与 R-3。
- **已知边角与兜底（v3.1 登记，QA-C23-04）**：第 1 步判据为 `adoptedRec?.channel !== undefined`。正常写入路径不会产生 `null`（`DshRecord.channel` 类型为 `channel?: string`），但 `readInstance()` 读的是磁盘 JSON——若 `instance.json` 被外部写成 `"channel": null`，运行期该值为 `null`，`null !== undefined` 为真，于是 `attachedChannel = null` 而 `attachedChannelSource = 'registry'`（值为空却带了来源标注）。**用户不可见**：快照层的配对不变式防御（`src/launchInfo.ts` 的 `channel === null → channelSource = null`）会把它纠正为 `null`，快照与渲染仍走 B3（显示「未知」+「运行通道无法核实」），不渲染来源标注；QA 代码检查已用独立脚本实测该防御生效（`INV_null_channel_source = null`）。**后续收窄建议（本轮未改，留待后续）**：可把第 1 步判据由 `!== undefined` 收窄为 `typeof adoptedRec.channel === 'string'`，或在 `DshRecord` 读取侧做一次归一——两者都能在源头消除该边角；当前有快照层兜底，不动代码。

| 分支 | 条件 | 现状行为 | v2 行为 | 说明 |
|---|---|---|---|---|
| ① 新 pid（`keepDshStartedAt` 假） | — | 取 `attachedChannel ?? undefined` | 同现状 | managed 拉起写 `options.channel`；external 恢复失败不写（维持 0.1.21 诚实缺省的边界） |
| ② 同 pid 重新认领，旧记录**有** `channel` | `prev.channel !== undefined` | 取 `prev.channel`（保留原值） | 同现状 | keep-reuse：注册表真值不因认领窗口漂移 |
| ③ 同 pid 重新认领，旧记录**无** `channel` | `prev.channel === undefined` | 取 `prev.channel` = `undefined` → **不写**（闭环继续） | 取 `attachedChannel ?? undefined` → **本次恢复成功即写入** | **这正是打破 §3.2「不写 → 读不到 → 显示未知 → 仍然不写」闭环的那一步**。v1 的表达式写对了行为但没有把「与现状的分道」说出口；v2 在此显式列出 |

分支 ③ 里 `attachedChannel` 的取值由 §5.2.1 保证：旧记录无 channel → 第 1 步不命中 → external 走第 2 步恢复 → 成功则有值（写入）、失败则 null（不写，维持诚实缺省）。因此表达式本身不需要额外条件。

一个如实披露的边界：分支 ③ 若本次认领**不是** external 路径（例如 0.1.21 之前的旧 managed-own 记录缺 channel、同 pid 再被 adopt），则 `attachedChannel = null`（非 external 不触发恢复）→ 不写，与现状一致，零回归。

`attachedChannelSource` 与 `attachedChannel` 一起在 `beginAttachment()` 的 per-attach 重置段（现 L461）与各清理点（现 L1458 / 1485 / 1512 / 1543 / 1602 / 1703）置 null，防止跨附着泄漏。

### 5.3 渲染侧判定修正（v2 按 QA-D23-07 修订）

`channelSource` **进快照**（`DshLaunchInfo` 第 21 个可选字段，字段定义见 §5.9），因此 `webviewDetails.ts` **零改动**——`buildDetailsHtml(info, phase, opts)` 已经拿到整个快照，`channelSwitcherHtml` 直接从 `info` 读值与来源，不存在第二条取值路径（QA-D23-01 三处矛盾由此收敛：v1 的「不进快照」表述作废，v1 改动点清单中 `webviewDetails.ts` 一项删除）。

`src/webviewHtml.ts` 的 `channelSwitcherHtml` 判定改为三态，来源标注**随 `channelSource` 渲染，不写死**：

```ts
// 判定逻辑（设计稿）
const cfg = ...  // configChannel，非空时有效
const running = current                                    // string | null
const pending = running !== null && cfg !== null && cfg !== running   // ← 关键修改：加 running !== null
const sourceNote = running !== null
  ? (channelSource === 'cmdline'         ? CHANNEL_SOURCE_NOTE_CMDLINE
     : channelSource === 'registry'      ? CHANNEL_SOURCE_NOTE_REGISTRY
     : channelSource === 'launch-option' ? CHANNEL_SOURCE_NOTE_LAUNCH_OPTION
     : '')
  : ''
```

三条分支（`{note}` 为占位，按 `channelSource` 取上面三个单点常量之一）：

| 分支 | 条件 | 「当前」行渲染 | 括号提示 | 重启按钮 |
|---|---|---|---|---|
| B1 运行通道可知且与配置一致 | `running !== null && cfg === running` | `当前 <b>{running}</b>（{note}）` | 不渲染 | 不渲染 |
| B2 运行通道可知且与配置不一致 | `running !== null && cfg !== running` | `当前 <b>{running}</b>（{note}） （已选「{cfg}」，待重启生效）` | 渲染（文案不变） | 渲染（`apply-channel-restart`，external 下仍走 external-hint 手动指引） |
| B3 运行通道不可知 | `running === null` | `当前 <b>未知</b>` | 改为：`buildChannelUnknownNote(cfg)`（即「（运行通道无法核实，配置为「latest」）」，单点函数） | **不渲染** |

B3 的处理是本轮的一处**语义修订**，需要说明理由与替代方案：

- **为什么改**：`pending` 的本义是「配置与运行不一致」。`running === null` 时这个判断在信息上不成立，恒真只是实现细节的副产物。渲染一个无法被验证的「待生效」断言，正是用户报的第二个现象。
- **改后是否丢掉了 0.1.21 想保的东西**：没有。0.1.21 真正要保的是「**不要假装配置已经生效**」。B3 的替换文案如实陈述了两件事——运行通道不知道、配置是什么——没有做任何「已生效」的暗示，保住了原目标。
- **替代方案（供用户评审选择，与 O-23-4 绑定）**：若用户认为「运行通道不可知时仍应保留按钮，让用户能主动重启对齐」，则可把 B3 定为「保留按钮 + 保留提示 + 附注『运行通道无法核实』」。本文的默认设计取「不渲染」，理由是：在我们无法知道当前跑什么的情况下，让用户点一个承诺「重启后生效」的按钮，本身就是不可兑现的承诺。此点列为开放项 O-23-1，**并与其绑定的既有断言反向改写（O-23-4）交同一次用户裁决**。

**配对不变式（v2 新增，可测试）**：`channel === null ⟺ channelSource === null`。两个方向：来源存在必说明渠道；渠道不明必无值。`buildLaunchInfo` 做防御：输入 `channel === null` 而 `channelSource` 非空时，强制把 `channelSource` 置 null（CH-23-4 有对应断言）。

### 5.7 可维护性分析

- **判定集中在纯模块**：通道恢复算法（`channelProbe.ts`）与渲染判定（`webviewHtml.ts`）都是纯函数，改动影响面可由测试直接钉住。
- **哈希算法是外部契约**：目录名算法是 npm 的实现细节（`libnpmexec`）。若上游修改算法，恢复会自然回落到「未命中 → 未知」，属安全失效，不会给出错误通道。为便于追查，恢复失败时须写 rlog（含命令行片段与提取到的目录名），使失效可被观测而不是静默。
- **规范形集合来源单一**：通道集合取自 `channelSelect.ts` 的 `DSH_CHANNELS`，包名取自 `dshResolver.ts` 的 `DSH_PKG`，新增通道时只需改那一处，反查表自动跟随。
- **语义分离**：值（`channel`）与来源（`channelSource`）成对传递，且被配对不变式（§5.3）钉死，杜绝 UI 层把间接事实说成直接事实的情形；来源标注字面单点定义在 `channelProbe.ts`（§5.1），渲染层禁止就地书写（沿用 `launchInfo.ts:230/235` 的文案单点纪律）。
- **与版本语义域的边界**：`CHANNEL_SOURCE_NOTE_CMDLINE` 与既有 `EXTERNAL_VERSION_NOTE_CMDLINE` 字面相同但**分立定义**——版本证据与通道证据是两个语义域，将来任一侧改文案不连带另一侧（§5.1 注释已写明）。

> **v3 更正说明（QA-D23-04 残留 / QA-D23-r2-01）**：v2 表里 discovery-port 行写「认领前已持有命令行 = 是（`runtime.ts:1309` 同型）、新增查询 0（复用）」，这一行**不成立**。`runtime.ts:1309` 虽把 `cmdline` 写入 `this.externalCommandLine`，但随后的 `discoveryAdopt`（L1346）第一句 `beginAttachment()`（L1347 → L452）在 `adopt`（L1349）之前就把该字段置 null——QA r2 的动态对照探针实测 discovery-port 路径在 `adopt` 入口读到 `null`，故 v2 的「字段复用」机制在这条路径上**永假**，实际必然落到 2b 对同一 pid 重复查询一次。v3 采纳 QA 推荐方案 A：改为**显式传参**（`discoveryAdopt`/`adopt` 新增可选第 6 参 `knownCommandLine`），把 `discoveryTick` 本 tick 已取到的完整 `cmdline` 直接带进 `adopt`，从而在该路径上真正做到新增查询 0。下表与 §5.2.1 机制、R-3、§12.3 已同步更正。

> **discovery-port 退化子情形（v3.1 登记，QA-C23-03）**：「新增查询 0」的成立**前提是本 tick 已经取到命令行**。当 `discoveryTick` 的 `processCommandLine(holder.pid, 15_000)` **本轮即返回 `null`**（CIM 不可用的既有降级分支，`runtime.ts` 该分支有 rlog「CIM unavailable; recording holder pid on page-signature basis」）时，本 tick 的局部 `cmdline` 与 `tickCmdline` 均为 `null`，作为第 6 参传 `null` 进入 `adopt`，于是走 §5.2.1 第 2b 步对**同一 pid 再查一次** `processCommandLine(pid, 15_000)`——最坏再叠加一次 15 s 同步阻塞（第一次查询的 15 s 是既有代码，本次新增的是第二次）。**该行为是代码忠实执行 §5.2.1 第 2b 步回退设计的结果，不是实现偏离**；影响面仅限「CIM 不可用」这一本身已处于降级的环境，不涉及正确性、数据目录与杀进程红线。**本轮不做短路优化**：这是退化子情形，且短路需先修订 §5.2.1 第 2b 步的规格（属设计变更），改动成本高于收益；口径以此处为准（QA 代码检查 QA-C23-03 已登记该子情形，判定为「成本表表述不精确」而非实现偏离）。

**频率上限**：新增查询只在「注册表记录缺 `channel` 字段」时发生（§5.2.1 第 1 步跳过判据）。首次恢复成功 → `writeRegistry` 写回 → **同一外部进程之后的一切同 pid 认领（任何窗口）零查询**。因此 15 s 预算是「每个外部 dsh 进程生命周期至多一次」，不是每次附着一次。

**阻塞影响的如实披露**（v1 未说清，v2 补全）：

1. `processCommandLine` 是**同步** `spawnSync`（`instance.ts:510-514`），最坏 15 s 期间**扩展宿主事件循环被阻塞**——不是单纯「ready 首帧延后」那么轻。既有代码在 step2（L518）与 discovery-port（L1306）已有同款调用，即该模式是项目已接受的先例；v2 把同型调用扩展到 step1 / step4 / discovery-registry 三条此前没有的路径，如实披露。
2. 典型 WMI 冷启动 0.5–3 s（`instance.ts:211` 注释先例），15 s 是超时上限而非常态。
3. 用户当前场景（step2 端口探测接管，探针 2 实证）**零新增查询、零新增阻塞**。v3 方案 A 落地后，**step2 与 discovery-port 两条主路径均为新增查询 0**；实际承担 15 s 同步查询的只剩 step1 / step4 / discovery-registry 三条路径，且都只在该外部进程生命周期首次（记录缺 `channel` 时）。
4. 阻塞发生在 `starting` 态内（`adopt` 在 `setState('starting')` 之后），面板已有 starting 过渡，不改变状态机顺序；恢复结果在 `refreshLaunchInfo`（L984）之前完成，首帧快照即携带恢复值，**不引入二次渲染**。

**为什么不改成异步（决策记录 DR-23-8，v3 更正理由不再依赖「discovery-port 零成本」旧断言）**：异步化需要给 `instance.ts` 的 `processCommandLine` 增加 async 变体或包装（改动其纯函数契约与既有 2 个调用点 `runtime.ts:518` / `:1306`），而收益只是把 15 s 的「事件循环阻塞」变成「该窗口附着链变慢」。考虑到（a）频率上限是「每进程一次」（首次恢复成功后注册表写回、之后同 pid 零查询）、（b）两条用户可感知的主路径（step2 冷启接管、discovery-port 停止态定期重连）经 v3 方案 A 后**均不新增查询**、真正承担 15 s 同步查询的 step1 / step4 / discovery-registry 只在「记录缺 channel」的边缘场景出现、（c）同步模式是项目既有先例（step2 / discovery-port 同型），v3 选择保持同步、如实披露成本，不扩大改动面。若用户评审认为 step1 / step4 / discovery-registry 的 15 s 事件循环阻塞不可接受，可另立事项做异步化——**该决策的理由与 discovery-port 是否零成本无关**（v3 已用显式传参把它做成 0，但即使不做，异步化的取舍仍由上述 (a)(b)(c) 决定）。

### 5.9 快照字段定义（v2 定案，QA-D23-01）

`src/launchInfo.ts` 的 `DshLaunchInfo` 接口新增第 21 个可选字段，`LaunchInfoInput` 同步新增对应输入，`buildLaunchInfo` 透传并做配对不变式防御：

```ts
// src/launchInfo.ts（设计稿）
export interface DshLaunchInfo {
  // …既有 20 个字段不变（dshVersion … externalCmdlineVersion）…
  /**
   * 快照 channel 字段的来源标注（0.1.23 新增，第 21 个字段）。
   * additve 可选字段，先例：externalUrl（#16）/ processStartedAt（#17）/ external 三字段（#18-20）。
   * 配对不变式：channel === null ⟹ channelSource === null（buildLaunchInfo 强制）。
   */
  channelSource?: ChannelSource
}
```

关键取舍：**为什么进快照而不是另开 runtime getter**。

- 来源与值必须同源，否则可能出现「值来自快照 A、来源来自 getter B」的失同步；
- 走快照后 `webviewDetails.ts` 零改动（`buildDetailsHtml` 已收到整个 `info`），改动面反而更小；
- 代价是快照键数 20 → 21，触发 `PP-12-2③` 需修订（§7.3），这是本轮**已知并已排期**的连带改动，不是意外。

### 12.3 派单问题 5 的答复（`externalCommandLine` 复用与否）

QA r1 提出的成本节省建议：step2 路径已经在 `src/runtime.ts:522` 把命令行写入 `this.externalCommandLine`（300 字符截断），恢复链可以直接复用它，免掉第二次查询。

**v2 决定：复用，不接受重复查询。** v3 在保留该决定的前提下，**更正了 discovery-port 的复用媒介**（v2 误写为「字段复用」，实际因 `beginAttachment()` 重置顺序不可能成立，改为方案 A 显式传参）；并更正了探针 7 的下标口径。依据与边界：

1. **必要性成立**：`runtime.ts:522`（step2）与 `:1306`（discovery-port）两处在上游已取到命令行，是本次修复覆盖的**主路径**（用户当前场景正是 step2，探针 2 实证）。**v3 更正**：step2 经实例字段 `this.externalCommandLine` 复用、discovery-port 经 `discoveryAdopt`/`adopt` 新增的可选第 6 参 `knownCommandLine` 显式传参复用，使这两条路径的**新增查询次数均为 0**（v2 曾写「discovery-port 也走字段复用」，QA r2 实测该字段在 `adopt` 入口已被 `beginAttachment()` 置 null、字段复用永假，故本版改为显式传参）。§5.8 成本表、§5.2.1 机制、R-3 均据此改写。
2. **截断安全性已实证**（探针 7，v2 新增证据、v3 更正下标口径）：本机命令行全长 130 字符，`_npx` 目录片段（含分隔符与 `_npx` 字样）位于下标 54–77，其中 **16 位目录名本身位于下标 60–75**；300 字符截断后目录名（60–75）仍完整在场、可完整提取。把前缀拉长到极端长度重跑，目录名依然在场。截断的失效方向是**token 缺席**（提取不到 → 诚实降级），不会截出假目录名。（v3 更正：v2 把「正则片段跨度 54–77」误写成「目录名位置」，QA-D23-r2-02 指出后已区分两个口径。）
3. **失效兜底**：若某环境下截断确实丢掉目录名，§5.2.1 第 2b 步仍会补一次完整查询（`processCommandLine(pid, 15_000)`）；再失败则回落 `channel: null`，不阻断生命周期。故复用不引入新的错误面，只引入「可能多一次查询」这一退化路径。
4. **明确排除的做法**：不为了「少一次查询」而放宽截断长度（`EXTERNAL_CMDLINE_MAX` 是 `launchInfo.ts:43` 的既有常量，服务于快照展示，不宜为本次修复改动）；也不新增第二条命令行缓存。
