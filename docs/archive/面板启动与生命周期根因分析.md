## 零、TL;DR（结论）

**四个问题不是一个缺陷的各面，而是同一条「托管启动 + 生命周期归属」模型不完整、且当前以 HTTP 探测为核心的端口占位判定存在设计缺陷的直接症状。收敛后的单一心智模型：`dsh = 共享常驻服务`（与手动 cmd 起的 dsh 同构、可复用），插件 = 轻量客户端（只做 discover / adopt / attach / record，不做 spawn 所有权 + 不做无条件 kill）。**

- **问题 1（卡启动中）**：根因 = **端口占位探测缺陷**。`portBusyByNonDsh()` 只用「HTTP 响应者」判断端口忙；当 3080 被一个**非 HTTP 响应**的暂态进程/挂起 dsh 占住时探测返回 `false`，插件仍按 3080 spawn → dsh 自身 bind 遇 `EADDRINUSE` → `exit code 1` → 按 1→2→4→8→16→32s 无限重启同一错误 → 卡「starting」，最终 `giving up`（error）。**探针 `probe-busy.mjs` 已实证该探测假阴性**。正则不匹配（c）与 npx 挂起（b）被排除或为次级。（详见 §1）
- **问题 2（部署/进程模型）**：托管 dsh = **扩展宿主进程（VSCode 的 Node 进程）内的 `cmd /c npx …` 子进程树**（`windowsHide:true`、stdio pipe），**非独立/分离进程**。部署位 = `%LOCALAPPDATA%\DshVscode`（协调注册表/锁/日志）+ npx 缓存 `%LOCALAPPDATA%\npm-cache\_npx\<hash>\node_modules\@deepseek-ai\dsh`（dsh 安装）+ `%USERPROFILE%\.dsh`（dsh CLI 数据/配置）。手动 cmd 起的 dsh 是独立进程，插件只 adopt。**v2 决策：本迭代直接落地 detached 独立进程**，让插件第一次 Lite 扳机拉起的 dsh 与手动 cmd 起的同构（详见 §2 与 §6.4）。（详见 §2）
- **问题 3（顶部标签）**：v4 只在 url 已知时静态置**iframe 可见 + overlay 隐藏**，但**顶部 `<span id="state">` 仍停留在静态占位 `initialising…`**，仅当页面脚本收到 `state` 消息才更新。若脚本晚执行/消息未达，iframe 已显示内容而顶部标签残留 —— 矛盾观感。方案：**url 已知烘焙时同步静态置顶标签**。（详见 §3）
- **问题 4（stop/restart 杀 dsh）**：`dsh.stop`→`stopManaged()`→`treeKill(托管子进程树)`；`dsh.restart`→`stopManaged()+start()`。对外部 adopt 进程虽不杀但清注册表/置 `stopped`，语义混乱。与「restart/stop 只影响扩展自身连接、最后窗口才停 dsh」的期望矛盾。**v2：detached 化使「stop/restart 不杀」天然成立，无需 child-managed 中间态**。（详见 §4）

**收敛方案**（§6）：把「spawn 托管」降级为**受管启动**（`managed launch`，detached 独立进程 + 非所有权），并修正端口占位判定为**通用 TCP bind 探测**；restart/stop 改为**不杀 dsh 的 client 语义**；同时静态烘焙顶部标签。**v2 把 detached managed-own 独立进程从「P1 后续」提升为本迭代唯一实施基线（新 P0）**——不再保留「既有子进程 + 停止语义改造」的 P0 中间态（原 F1「未分离子进程却『不杀』」的自洽缺口随之消失，因为不再有 child-managed 中间态）。注册表 `dsh` record 仍为**权威重发现来源**：异常退出残局由下一窗口 **re-adopt 重接管**回归、外部非默认端口以 **known-external 保留**避免不可达（关闭 QA BLOCK F1 / RECOMMEND F2 的闭合语义保留），并把 bind host 抽为**单一来源 `LOOPBACK_HOST` 常量**（F3）。四者共同落进 `dsh = 共享常驻服务`模型。

## 一、问题 1：插件-only 卡「启动中」

### 1.1 5-Why

| # | 现象/回答 | 依据 |
|---|---|---|
| W1 | 为什么只开 VSCode（不手动起 dsh）时面板一直卡「启动中」，也不主动拉起 dsh？ | runtime.log 04:02 进入 spawnManaged，随后 6 次 `crashed` 后 `state: starting -> error`。`ready` 全部来自 adopt(external)，托管 spawn 无一次成功记录。 |
| W2 | 为什么托管 spawn 反复崩？ | dsh.log 04:52-04:54：`Error: listen EADDRINUSE: address already in use 127.0.0.1:3080` + `exited: code=1`，restart #1..#6。 |
| W3 | 为什么用 3080 去 spawn，而不是先回落随机端口？ | runtime.ts `spawnManaged()` L141-145：仅当 `portBusyByNonDsh(3080)` 为真才回落 0；`:234-241` 该方法**只用 HTTP GET** 判定端口忙。该次日志无 `falling back`，说明它返回了 `false`（判定 3080 空闲）。 |
| W4 | 为什么 `portBusyByNonDsh(3080)` 返回 false，而真实 bind 却 EADDRINUSE？ | 端口被一个**可 TCP accept 但不回 HTTP**的暂态进程占住（如被 taskkill 的上一 dsh 的滞留监听、或正在初始化未起 HTTP 的 dsh）。HTTP 探测对这种占位**假阴性**：`fetch` 超时→catch→`false`。 |
| W5 | 根因是否成立？ | **成立**。探针 `probe-busy.mjs` 实证：`portBusyByNonDsh(非HTTP占位端口)=false`，而同一端口 `bind()`=`EADDRINUSE`。⇒ 判忙手段与真实 bind 冲突判定不一致 → 必然误判。 |

### 1.2 假设列表与验证

| 假设 | 验证方法 | 结果 |
|---|---|---|
| (a) 端口占位探测缺陷（HTTP-only） | `probe-busy.mjs` 复现 + 日志横断 | ✅ **主根因** |
| (b) cmd/npx 在隐藏窗口下挂起（网络/registry/缓存锁） | 日志无「一直无输出」；EADDRINUSE 明确先于一切 | ❌ 无直接证据；且即便挂起，也不会报 EADDRINUSE。降级为**次级风险**（见 §6.5 兜底） |
| (c) URL 正则与实际 dsh 输出不符 → 解析不到端口 → 永不 emit 'port' | 读 dsh 源码：`printUrl` 默认 true、`LOOPBACK_HOST="127.0.0.1"`、横幅 `dsh web: http://127.0.0.1:<port>` 仅于 loader settle 后打印 | ❌ **排除**（成功启动时正则完全匹配） |

> 关键裁决：**(c) 被排除**——真实 dsh 成功启动时的 stdout 行 `dsh web: http://127.0.0.1:3080 (LAN: …)` 正好被 `URL_RE = /dsh web:\s+(http:\/\/127\.0\.0\.1:(\d+))/i` 匹配。**但**，横幅仅于**loader/plugin tree settle 成功**后才打印（`dsh-web-app` L194-212 `announceReady`）。因此「端口已被占导致 bind 失败 → 进程在 settle 前 exit 1」时，**横幅根本不会出现**——这放大了 (a)：失败进程既不打印 URL，插件也无从 fallback，只能干等退避重启。二者叠加才构成「看起来没在拉 dsh」的用户观感。

### 1.3 探针数据
- `probe-busy.mjs` 实跑输出（摘要）：
  ```
  portBusyByNonDsh(HTTP)    = true
  portBusyByNonDsh(nonHTTP) = false  (假阴性)
  fresh bind on nonHTTP port = EADDRINUSE
  VERDICT: DEFECT CONFIRMED
  ```
- 日志横断（04:02-04:54）：`portBusyByNonDsh(3080)` 假阴性 ↔ dsh bind EADDRINUSE ↔ 退避重启 #1..#6 ↔ `giving up`。

## 二、问题 2：托管 dsh 部署在哪 / 为什么不是独立进程

### 2.1 事实（源码 + 路径核实）
`dshProcess.ts` L75-79 + L110-129（现状）：
- 托管 = 扩展宿主（extension host，一个 VSCode 的 Node 进程）内 `spawn('cmd.exe', ['/d','/s','/c', 'npx --yes --prefer-offline @deepseek-ai/dsh@latest web --host 127.0.0.1 --port <p> --no-open'])`，`windowsHide:true`，stdio `['ignore','pipe','pipe']`。
- 因此进程树：**扩展宿主 pid → cmd.exe → npm/npx → node bin.js（dsh）**。PPID = 扩展宿主；dsh 不是 detached/独立进程，**随扩展宿主生命周期被拉起，但其生存可由插件 kill/保留**。

部署位置（多层）：
| 数据 | 路径 | 性质 |
|---|---|---|
| 插件协调注册表/锁/日志 | `%LOCALAPPDATA%\DshVscode\{instance.json, startup.lock, logs\*}` | 插件自管，与 dsh 本体无关 |
| dsh 安装（含依赖） | `%LOCALAPPDATA%\npm-cache\_npx\<hash>\node_modules\@deepseek-ai\dsh` | npx 按需装；实测插件缓存 hash=`b86ed90107c62dab`，dsh `0.1.1-rc.2` |
| dsh CLI 数据/配置/会话 | `%USERPROFILE%\.dsh\{settings.yaml, profiles, sessions, storages, ...}` | dsh 本体自管（DSH_HOME 可经配置覆盖） |
| 会话/工作区状态 | `%USERPROFILE%\.dsh\sessions\--<path>--\*` | 按工作区哈希分目录 |

手动 `cmd npx @deepseek-ai/dsh web` 起的 dsh 是**独立进程**（脱离 VSCode），插件只 adopt（`adopt(port, pid, 'external')`，runtime.ts L181-188）。

### 2.2 回答用户 + 权衡（v2：直接上 detached）
用户问：为什么不启动一个独立 dsh 进程（像手动 cmd 那样）？
- **现状**：托管 = 扩展宿主子进程，优点是无需用户动手、日志/regex 可观测；缺点是**所有权附着于扩展宿主**（随宿主结构绑定）、一个宿主进程管理不够"系统级常驻"。
- **期望**：dsh = 共享常驻服务，像手动 cmd 起的一样独立、可被多窗口/多工具复用，重启/停插件不影响它。
- **v2 方案（用户评审已定）**：**本迭代直接实现 detached 独立进程**，不做「既有子进程 + 停止语义改造」的中间态。引入「**受管启动（managed launch）**」形态：由插件第一次 Lite 扳机无 dsh 时代拉一个 `detached:true` 的独立进程，`windowsHide:true`、stdio 重定向到数据目录日志文件（非 pipe）、不 wait、不持有句柄——使其脱离扩展宿主成为真·独立常驻（Windows 无 Unix 风格 re-parenting；以「PPID 不再指向扩展宿主」为脱离生效的可观测判据）。这与手动 cmd 的 dsh 同构，区别仅在于「由插件代拉」。做成 vs 不成的权衡见 §6.4。

> v2 一致性说明：因不再有「child-managed 子进程中间态」，原 P0 下「未分离子进程却『不杀』」的自洽缺口（原 F1 残留孤儿/端口残留）从进程模型上消除——detached 进程本就设计与宿主解耦，`stop/restart 不杀`无需自洽修补即天然成立。残余风险（异常退出后无人打开 VSCode 时的常驻残留）见 §6.4，属 detached 的「有意常驻」语义而非 child 中间态缺口。

## 三、问题 3：顶部标签残留「initialising…」

### 3.1 根因（真实 + 矛盾观感）
`webview.ts html()` v4（f859313）：url 已知时**静态**烘焙 iframe `src` + `display:block`（L244）+ overlay `.hide`（L245）；但**顶部 `<span id="state">initialising…</span>`（L276）是纯静态文本**，只在页面脚本收到 `state` 消息后才 `textContent = 'dsh · '+url`（L318）。即：**iframe 层 100% 静态就绪，状态标签仍依赖脚本/消息回环** —— 二者不同步。
若页面脚本晚执行、或被 CSP 挡掉、或消息在 dispose 竞态丢失（0-handshake 曾因于此，现由握手+补推缓解但仍非静态），顶部就永远「initialising…」与已显示的 dsh UI 自相矛盾。

### 3.2 方案
在 `html()` 内，**与 iframe/overlay 同一静态烘焙点**决定顶部文案：
```
known ? `<span id="state">dsh · ${escape(url)}</span>` : `<span id="state">initialising…</span>`
```
脚本收到 `state` 消息后照常覆盖（增强层）。**不新增 host/port/https 字面量**，值仍来自 `runtime.url`（去硬编码约束保持）。这样即使脚本完全不执行，顶部标签也与 iframe 一致地显示「dsh · http://127.0.0.1:<port>」。
> 语义见 §6.3：状态标签文案统一走「ready → `dsh · <url>`」；非 ready 显示 state 原文 + 可选 error（错误仍由脚本展示，静态只覆盖 ready 与非 ready 的通用占位）。

## 四、问题 4：stop / restart 会杀 dsh —— 与共享资源期望矛盾

### 4.1 现状事实
| 命令 | 实现 | 对 dsh 的影响 |
|---|---|---|
| `dsh.restart` | extension.ts L85-88 → `runtime.restart()`（L301-306）→ `stopManaged()` 再 `start()` | `stopManaged`→`this.process.dispose()`→`DshProcess.stop()`→`treeKill(子进程树)`（L159-177）⇒ **杀托管 dsh**；对外部 adopt（process=null）不杀但清注册表+置 stopped |
| `dsh.stop` | extension.ts L89-91 → `runtime.stopManaged()`（L286-298） | 同上 ⇒ **杀托管 dsh**；对外部不杀但清注册表+`state:'stopped'` |
| 最后窗口关闭 | extension.ts `process.on('exit')`→`shutdownBookkeeping()`（runtime L250-283）三重防误杀后 `treeKill` | 按设计杀 dsh（用户认可「最后窗口才停」） |

矛盾：用户期望 **restart/stop 不关停 dsh**；只有最后一个 window 关闭才停 dsh。且「stop 生成 dsh 后必须手动再 start」对共享服务语义尤其混乱。

### 4.2 目标语义（用户需求）
- `restart`：仅代表「扩展重新 discover/adopt/attach dsh 连接」，**不 kill dsh**；若 dsh 已不在（外部被手动关了），则走启动路径把它拉起。
- `stop`：仅表示「扩展断开/不再占用」，**不 kill dsh**；dsh 继续作为共享服务存在，别的窗口/工具仍可使用。
- 只有**最后一个窗口关闭**（`shutdownBookkeeping`）且确认真为该 dsh 时才停 dsh —— 保留现有三重防误杀。
- 对「托管」这一形态：`managed launch`（detached）的归属规则使「插件不 kill」天然成立（§6.4）。

> **v2 一致性说明**：原 v1 因 P0 是 child-managed 中间态，需显式声明「stop/restart 不杀」在 P0 的收敛边界（只承诺不 kill + 注册表保留，不承诺异常退出也干净），并对 child-managed 的 Windows 孤儿残留做自洽修补。**v2 直接 detached 化后，该中间态的残留缺口从进程模型上消失**：detached 独立进程不会因扩展宿主异常退出而变「孤儿 + 端口残留」缺斤短两（它本就独立常驻），`stop/restart 不杀`对 detached 天然成立，问题 4 的方案不再依赖问题 1/2 之外的中间态修补（残局 re-adopt 与 known-external 保留仍保留，作为注册表权威重发现的兜底收敛，见 §6.4）。

## 五、目标 / 范围

**目标**：让「VSCode 插件访问 dsh」与「用户手动 cmd 起 dsh」体验一致——dsh 是共享常驻服务，插件是轻量客户端；修复卡的启动路径、理清部署/进程模型、同步顶部标签、让 stop/restart 不杀 dsh。落成**一份**多角色可执行的技术设计（含 A1 链继续所需的时序/状态机、决策记录、实施清单、自动化判定）。

**做（范围）**：
- 重设计并修正端口占位判定（通用 TCP bind 探测），消除 EADDRINUSE 崩溃循环。
- 把「托管 spawn」重构为「**受管启动 managed launch（detached 独立进程 + 记录 non-ownership）**」并作为**本迭代唯一基线**（新 P0）：插件代拉的 dsh 为 detached 独立常驻，不再有「既有子进程 + 停止语义改造」的 child-managed 中间态。
- restart/stop 语义改为不杀 dsh（client 语义），保留最后窗口关闭的停止（仅对 managed-own/extension，external 保留）。
- 注册表 `dsh` record 为权威重发现来源 —— 异常退出残局由下一窗口 re-adopt 重接管，外部（含非默认端口）最后窗口保留 known-external 记录（仅陈旧才清）。
- 顶部状态标签静态烘焙就绪文案。
- 全部参数/端口运行时/配置驱动，去 127.0.0.1/3080 字面量新增；bind host 抽为单一来源 `LOOPBACK_HOST` 常量（保留既有 CSP `frame-src http://127.0.0.1:*` 不变，属安全约束非端口字面量）。
- 补充可自动化判据（无头可跑）到 `sim.mjs`。

**不做（范围）**：
- 不把 dsh 打进扩展包 / 不改 dsh 本体（仍靠 npx `@deepseek-ai/dsh@latest`）。
- 不做「既有子进程 + 停止语义改造」的 P0 中间态（用户评审已明确直接上 detached 版，不保留中间态）。
- 不引入系统级服务/session 管理（异常退出后无人再开窗口时的常驻残留，其根治超出本项目范围，detached 下该残留为「有意常驻」语义，予以显式声明）。
- 不改 `shutdownBookkeeping` 最后窗口三重防误杀语义（用户认可）。
- 不做自指修改（修改本 preset/插件）——超 A1 工程范畴。
- 本设计**不实施**：实施/部署/QA 由后续角色承接。

## 六、技术选型及设计（架构 / 时序 / 状态机）

### 6.1 统一生命周期模型（心智模型）
```
dsh = 共享常驻服务（一个实例，监听一个端口，detached/独立于任何扩展宿主）
         ▲  discover / adopt / attach / record（不 kill）
         │
多窗口/多工具（VSCode 各扩展宿主、手动 cmd、浏览器……）
```
- **所有权（ownership）**：dsh 不「属于」任何扩展。只有一种特例「managed launch」：由插件在无任何 dsh 时**代拉**一个 detached 独立进程，但拉起来后插件仍视为可被外部复用、并可被最后窗口按规则停掉。
- **插件职责**：discover（注册表 + 端口探测）→ adopt/attach（记录窗口 + 持有连接状态）→ record（写 instance.json）→ attach 断开（unregister）→（可选，仅在确认无人用时）触发停止。

### 6.2 端口占位判定修正（问题 1 修复）
**坏**：`portBusyByNonDsh`（HTTP-only fetch）。
**好**：把「端口是否可 bind」作为判定依据——用**通用 TCP bind 探测**与 dsh 真实的 bind 失败保持一致：
```
# 单一来源 HOST 常量（去硬编码，F3；见 §8 与 ADR-8）
const LOOPBACK_HOST = HOST_CONST  // 与 dsh `--host 127.0.0.1` 同源（paths 层导出，供 runtime/dshProcess/probe/netstat 复用）
async function portBindable(port): boolean {
  return new Promise(resolve => {
    const srv = net.createServer()
    srv.once('error', () => resolve(false))       // EADDRINUSE / 无权
    srv.listen(port, LOOPBACK_HOST, () => { srv.close(() => resolve(true)) })   // host 走常量，不写字面量
  })
}
```
> F3 闭合：`portBindable` 的 bind 地址、`probe`/url 拼接、`dsh --host`、netstat 地址过滤统一引用 `LOOPBACK_HOST` 常量（单点来源），**不再新增 `127.0.0.1` / 3080 字面量**。CSP `frame-src http://127.0.0.1:*` 属安全约束，**维持硬编码与通配符不变**（QA 判定正确，不回退为模板）。
- `spawnManaged` 预检改为：`!await portBindable(usePort)` ⇒ 若不可 bind 则 `usePort=0`（回落随机），并记日志。
- 重启循环内**不再死磕同一端口**：每次重启若 `portBindable(usePort)` 假，直接 `usePort=0`（或提升重试/给 error），避免 6 次都撞同一 EADDRINUSE。
- **保留** HTTP `__DSH_BOOT__` 探测用于「adopt 一个已在跑的 dsh」语义（真正判是不是 dsh），与「判端口能否 bind」分离——语义分离约束。

> 时序（startup path，detached 基线）：
> 1. 注册表里有活 dsh 且端口 `probe`（HTTP+`__DSH_BOOT__`）通过 → adopt（不变）。
> 2. 否则探测配置端口：
>    - 若 `probe(port)` 真（HTTP+签名）→ adopt(external)。
>    - 否则若 `!portBindable(port)`（端口被非 HTTP 实体占）→ 记日志，**该端口视为被占**，不在此 spawn；可回落随机端口或用启动锁仲裁。
> 3. 第一窗口拿 `startup.lock` → `managed launch`（detached）→ **端口解析数据源（F-PORT，详见 §6.4.1）**：固定端口路径直接对该端口 `__DSH_BOOT__` probe；随机端口路径 tail 轮询日志横幅用 `resolvePortFromLog` 解析端口后 probe 确认 → 就绪 → 写注册表（`managedBy='managed-own'`）。
> 4. 第二窗口拿不到锁 → 轮询注册表 adopt（`waitForExternalStartup` 保留）。

### 6.3 顶部标签静态烘焙（问题 3 修复）
见 §3.2。状态标签文案契约：
- ready & url 已知 → 静态 `dsh · <url>`（同步 iframe）。
- 非 ready（starting/error/stopped/idle） → 静态占位 `starting…`/`error`，脚本覆盖增强。
- 一切文案值来自 `runtime.url`/`runtime.state`/`runtime.errorMessage`，无字面量。

### 6.4 managed launch（detached 版本轮实施：独立进程 + 非所有权 + 停止权）

把 `dshProcess.ts` 从「子进程监督 + 所有权」改为「**受管启动器 + 记录器；spawn 后不 wait、不持有句柄**」。**detached 化是本迭代唯一实施基线**，不再有「既有子进程 + 停止语义改造」的中间态。

#### 6.4.1 spawn（detached）实现要点（Windows）
```
# dshProcess.ts 的 launch（替代现有 spawn/child 持有）
spawn(exec, argv, {
  detached: true,        // 关键：脱离父进程，新进程组；释放句柄后其 PPID 不再指向扩展宿主
  windowsHide: true,     // 不弹黑窗
  stdio: ['ignore', fd-out, fd-err],   // 重定向到 %LOCALAPPDATA%\DshVscode\logs\dsh-<ts>.log，
                                       // 不再 pipe 到宿主（避免 EPERM 边界 + 消除 stdout 攒积）
})
child.unref()            // 关键：父进程不等待/不持有句柄，使 dsh 真正独立常驻
```
**风险规避要点**：
- **不 wait、不持有句柄**：`spawn` 后**立即 `unref()`**，插件不监听该 child 的 `exit` 事件作为生命周期依据（detached 下 exit 无意义，进程可能比插件活得久）。
- **进程归属**：detached 后 dsh 进程组脱离扩展宿主（Windows 无 Unix 风格 re-parenting，故以「其 PPID **不再指向扩展宿主**」作为脱离生效的可观测判据，而非「PPID=0/System」）；扩展宿主退出不影响 dsh 存活。
- **日志重定向**：不等同于 `stdio:'ignore'`——推荐重定向到 `%LOCALAPPDATA%\DshVscode\logs\dsh-<ts>.log`（**不 pipe 到宿主**，规避沙箱 EPERM + 防 stdout 攒积；按日轮转，保留最近 N=3，防日志膨胀，§9）。若实现方选择先 `'ignore'`，则日志收敛交给 dsh 自身 `dsh.log`（`%USERPROFILE%\.dsh`），二者取其一并注明。
- **端口解析——detached 后的数据源决策（F-PORT 闭合，关键）**：detached + stdio 重定向到日志文件 + `unref()` 后，`child.stdout`/`stderr` 的 `on('data')` **不再可用**（pipe 被移除，`URL_RE` 失去原来的 stdout 数据源），故端口解析需**从文件读回**而非监听流。**可组合双路（方案 A + B）**，判定统一收敛到一个纯函数 `resolvePortFromLog(logFile): number | null`（复用 `URL_RE`，输入改为读文件）：
  - **方案 B（固定端口路径）**：当 `dsh.port` 配置为**固定端口**（默认 3080，且 `portBindable` 判定该端口可 bind、未回落随机）时，**无需解析**——直接以该固定端口对 `__DSH_BOOT__` probe 确认；此路径不碰 `URL_RE`，更快更省。
  - **方案 A（随机端口路径，一等路径）**：当 `--port 0` / 回落随机时，端口只能从 dsh 横幅得知 → **tail 轮询** `%LOCALAPPDATA%\DshVscode\logs\dsh-<ts>.log`（日志文件名与 P0-B spawn 重定向落盘一致）：周期（如每 500ms，受启动总超时 90s 约束）读文件尾部，用 `resolvePortFromLog` 匹配横幅 `dsh web: http://127.0.0.1:<port>`（`URL_RE`）取端口；拿到后在**启动总超时内对解析端口 `__DSH_BOOT__` probe** 确认就绪（防止正则命中但实际未就绪/横幅早于 bind）。
  - **去重**：方案 A/B 共用同一 `resolvePortFromLog`（`URL_RE` 单点）+ 同一事后 `__DSH_BOOT__` probe 封装；`waitReady(url)` 直接复用（§现有 `DshProcess.waitReady`），在启动总超时内完成「resolve/probe 就绪」循环，**不另写一套正则或轮询**。
  - **失败兜底**：驱动端口已知（固定）但 probe 直至总超时仍未就绪，或随机路径 tail 至总超时仍解析不到端口 → 判 `failed`（给出日志路径），按 §6.5 退避上限处理；**保证「随机端口路径可被解析且可 probe 确认」闭环**。

#### 6.4.2 探活 / 崩溃退出判定（detached 后不再监听 exit 的替代）
detached 后插件不再监听子进程 `exit` 事件 → **崩溃/退出依赖外部周期性探活**。设计探活策略与「判定 dsh 死 → 重新拉起」路径（不无限重启）：
- **探活源**：周期性（如每 30s；可配 `dsh.probeIntervalSec`）对记录端口做 `__DSH_BOOT__` probe；必要时辅以注册表 pid `isAlive` 检查（pid 存活但 probe 失败 → 端口异常，记日志区分）。
- **判定 dsh 死**：`probe(port)` 持续失败（连续 N 次，如连续 3 次）且（可选）pid 已死 → 判定该 dsh 已退出。
- **重新拉起路径（有界，不无限重启）**：
  - 插件当前处于 `ready`（本窗连接中）且探活判定 dsh 死 → 清陈旧注册表记录 → 走 start() 启动路径（若本窗持有 `startup.lock` 或仍是无 dsh 状态则 managed launch；否则 adopt 他人新拉起的）。
  - **防无限重启**：沿用**崩溃退避上限**（1→2→4→8→16→32s，6 次上限 → `error`，§6.5），且探活重拉计入同一重启计数；达到上限后**停止重拉**，转 `error` 并提示用户，不无限循环。
  - **边界**：探活重拉仅服务于「本扩展正在连接且 dsh 意外退出」的场景；若插件处于 `stopped`/未连接（用户已 stop），**不主动重拉**（避免「用户停掉又自动拉起」的意外）。
- **探活非实时**：detached 下无法即时感知 crash；判定粒度 = 探活周期，实时性降低可接受（dsh 常驻服务语义），文档/状态栏如实反映「已连接（探活中）」或「已断开（等待恢复）」。

#### 6.4.3 只在「当前无 dsh 可用」时做 managed launch
- **discover 失败才代拉**：仅在 §6.2 时序 1、2 均无可用 dsh 时才 `managed launch`；dsh 已存在（external adopt 或注册表 re-adopt）则不代拉、直接 adopt——与手动 cmd 同构。
- 这保证插件从不「抢跑」用户/其他工具已起的 dsh，managed-own 是「最后一手」的代拉。

#### 6.4.4 managed-own 的停止权
- **停止权**：仅「**最后窗口关闭 + 三重防误杀**」才停（用户认可）。三重防误杀保留：pid 存活 + 端口监听（`resolvePortPid` 核对） + `__DSH_BOOT__` probe 全过才 `taskkill /T /F`。
- `stop`/`restart` → `disconnect()`/`reconnect()`：**只 disconnect/reconnect，绝不 treeKill**（见 §6.4.5）。
- `external`（用户手动 cmd 起的）**不主动杀**；其记录在最后窗口时**保留**（known-external），仅陈旧（`probe` 失败 / pid 已死）才清，供下一窗口 re-adopt。

```
# 停止权矩阵
命令/事件            managed-own / extension      external（手动 cmd 起）
dsh.stop             disconnect（不 kill）        disconnect（不 kill）
dsh.restart          reconnect（不 kill）         reconnect（不 kill）
最后窗口+三重防误杀   taskkill /T /F → 清记录    不 kill；保留 known-external 记录（仅陈旧才清）
探活判定 dsh 死      清陈旧记录 → （本窗连接中）重拉  同左（连不回来即 stopped/error）
```

#### 6.4.5 client 语义落地
- `stopManaged()` → `disconnect()`：只清本窗口/本扩展的连接记录 + 状态 `stopped`；**绝不 treeKill**。
- `restart()` → `reconnect()`：discover→(adopt | 若无则 managed launch) 后 attach；**不 kill**。
- **`updateRuntime` 例外（F-UPDATE，见 ADR-10）**：`dsh.updateRuntime` **不复用 reconnect**，而是「**显式强制重拉（force relaunch）**」的受控例外——用户在其 modal 确认后，对 `managed-own` dsh 执行受控 kill + 重新 managed launch（npx 重新解析 latest）；对 `external`/已 adopt dsh **不 kill**，改为提示「版本更新需由手动 cmd 或受控重拉」。该例外仅在使用者主动确认「升级版本」时触发，与「stop/restart 不杀」语义不冲突（用户评审门确认）。
- `shutdownBookkeeping`：保留汇总见「§6.6 / §6.4.4」，仅对 `managed-own`/`extension` 且最后窗口才 treeKill；`external` 保留 known-external 记录。

#### 6.4.6 残局重接管 + known-external 保留（注册表权威重发现）
注册表 `dsh` record 仍是**唯一的、权威的重发现来源**（regardless of 端口/上一宿主生死）：
- **正常退出路径**：`process.on('exit')` → `shutdownBookkeeping` → 最后窗口 + 三重防误杀 → treeKill（`managed-own`/`extension`）或保留记录（`external`）→ 无孤儿。
- **异常退出路径（extension host crash / taskkill /F / 强制结束，exit 钩子不触发）**：detached dsh **不受影响，继续独立常驻**（这正是 detached 的本意），注册表 `dsh` record 保留（`managedBy='managed-own'` 或 `'external'`）。**兜底 = 下一窗口 `start()` 第 1 步注册表分支对「残留 managed-own」启用 re-adopt**：若 record 存在且 `isAlive(pid)` 且端口 `probe`（`__DSH_BOOT__`）通过 → 直接 adopt（`managedBy` 沿用原值），**不 spawn 新进程、不撞残留端口**；若 `probe` 失败/pid 已死 → 视为陈旧（dsh 确已退出），清记录后按 §6.2 走正常启动（可能需要重新 managed launch）。由此「任一时刻注册表指向的 dsh 要么可被下一窗口重接管（无不可达孤儿），要么已在正常路径被清理」。
- **外部非默认端口（F2）**：external 若在**非默认端口**（3080 被占回落 random），最后窗口**不再「清记录不杀」**，改为**「保留 known external 记录（port/pid/managedBy='external'）」**——只 unregister 本窗口，不删除该 external record，使下一窗口仍经注册表 adopt（无需依赖默认端口探知）。external record 的清除交给**陈旧判定**（`probe` 失败或 pid 已死），而非「窗口关了就删」。默认端口 external 同样适用该保留策略（统一规则，消除「非默认端口不可达」特例）。
- **残余风险（显式声明，detached 基线验收口径）**：若异常退出后**用户不再打开任何 VSCode 窗口**，detached dsh 将持续监听其端口直至被手动结束。**这在 detached 下是「有意常驻」，语义优于 child 中间态的残留缺口**（不是「被宿主强带的残缺孤儿」），且该残留端口带 `__DSH_BOOT__` 可被标识；缓解 = 文档/编辑器错误提示引导排查（rlog 打印「疑似上轮 detached 残留 dsh pid/port」，用户可按注册表或任务管理器结束）。完整根治需系统级服务/session 管理，超出本 A1 范围。

**做成 vs 不成的权衡**（detached 基线）：

| 维度 | 现状（子进程托管） | 方案（managed-own detached 独立常驻） |
|---|---|---|
| 复用/共享 | 绑宿主，多窗口靠注册表仲裁 | 真·独立常驻，与手动 cmd 同构 |
| stop/restart 不杀 | 不可能（所有权在插件） | 天然成立（detached 非所有权） |
| 崩溃退避监控 | 有（子进程监听） | 需**外部探活**（周期性 HTTP `__DSH_BOOT__` + 注册表 liveness），或有界重拉 |
| 实现成本 | 低 | 中（detached + 文件日志 + 探活 + 关停判定重构） |
| 异常退出孤儿 | P0 有（child 中间态残留缺口，v1 显式声明） | detached 下残留为「有意」常驻，语义不同、缺口消除 |
| 与手动 cmd 同构 | 否 | 是（用户评审明确期望） |

> **v2 取舍（用户评审已定）**：直接上 detached 基线，不做「子进程受管 + 停止语义改造」的 P0 中间态。**不再提供两档**——本迭代唯一基线是 **P0（detached managed-own 独立进程 + 外部探活 + client 语义 + 残局 re-adopt + known-external 保留）**。原 v1 的「P0 中间态 / P1 后续」分档取消。

### 6.5 崩溃退避兜底（npx 挂起的次级风险 + detached 探活重拉的界）
即便修好端口判忙，仍需防「cmd/npx 迟迟无输出」（网络/缓存锁）致卡 starting。兜底：
- 启动设**总超时**（如 90s）无『port 事件』→ 判 failed（给出日志路径供定位），不再无限退避。
- 退避策略改为**降级端口**：`portBindable` 假 → `usePort=0` 再起重试（避免同端口死循环）。退避次数上限保持不变（6 次 → error）。
- **detached 探活重拉复用同一退避上限**（§6.4.2）：探活判死 → 重拉计入重启计数，上限 6 次 → `error`；**不产生无限重启**。
- detached 下无 child `exit` 事件可监听，`start()`/launch 的失败判定改由「总超时 + 端口 probe 双保险未就绪」承担。

### 6.6 状态机（RuntimeState，detached 基线）
```
idle ──start()──> starting ──注册表 re-adopt(pid存活+__DSH_BOOT__)──> ready   (残局重接管，F1)
                      │        └─否则 managed launch: 端口解析+__DSH_BOOT__ 探针──> ready
                      ▼                                  ▲
                    error ◄──(giving up)── starting(6次) │ adopt(外部/known-record/managed-own)
   stopped ──disconnect()──> ready   (stop/restart 不 kill，仅去连接)
   ready ──disconnect()──> stopped（仅本扩展视图：dsh 仍常驻、记录保留）
   ready ──探活判死(连续失败+pid死, 带重启上限)──> starting（重新拉起，受退避上限约束）
   ready ──last-window+防误杀──> managed-own/extension: (taskkill dsh)→清记录；external: 不杀、保留 known-external 记录（仅陈旧才清）
```
状态机语义变更：`stopped` 仅表示「本扩展未连接」，不再等于「dsh 已死」。`dshAlive`/`probe` 独立判定 dsh 本体。注册表 `dsh` record = 重发现权威来源：正常路径由 `shutdownBookkeeping` 清理（managed）或按陈旧判定清除（external）；异常退出路径由 `start()` 第 1 步 re-adopt 兜底接管（F1/F2 自洽边界）。detached 基线新增 `ready ──探活判死──> starting` 边（受重启上限约束，不无限重拉）。

| 无头验证 | `npm run compile` 通过；`sim.mjs` 当前 ALL PASS、2 SKIP（sandbox netstat/taskkill 限制，QA 已定位，环境差异非缺陷） | 基线绿，可在其上追加 detached 用例 |

## 八、可维护性

- **语义分离**（约束）：「端口能否 bind」与「是不是 dsh」拆成两个独立函数（`portBindable` / `probe`），不再混用 HTTP 响应做两者判定。
- **单一心智模型**：`dsh=共享常驻、插件=轻量客户端` 贯穿 discover/adopt/disconnect/record，代码注释与文档同步。
- **去硬编码**：所有新增端口/超时/主机走 `paths`/配置；新增单一来源 `LOOPBACK_HOST` 常量（与 dsh `--host` 同源），`portBindable`/`probe`/url 拼接/`--host`/netstat 回环地址集合统一引用，**不再新增 `127.0.0.1` / 3080 字面量**（F3）；**豁免说明（F4）**：`URL_RE` 内的 `127.0.0.1` 字面量属**既有**（非本次新增），与 `LOOPBACK_HOST` 同源，保留原样、不参与「去硬编码」改造，避免被 F3 波及；CSP `frame-src http://127.0.0.1:*` 维持硬编码+通配符不变（安全约束，不模板化）。
- **进程模型单点**：managed launch / adopt / 停止 / 探活重拉逻辑收敛到 `runtime.ts`+`dshProcess.ts`，`extension.ts` 只挂命令与生命周期钩子；探活周期走配置 `dsh.probeIntervalSec`。
- 模块分层与纯 Node 无 vscode 依赖约束保持不变（可无头测试）。

## 九、性能（定量）

- 端口判忙 `portBindable`：单次 `net.listen` 往返 ~0-2ms（本机 TCP bind）；相较原 HTTP `fetch(1.5s 超时)`，**失败路径判定快 2-3 个数量级**（原最坏 1.5s，现毫秒级），并消除假阴性导致的 6×退避（1+2+4+8+16+32=63s 的无效重试）。
- 每窗口 `start()` 探测开销：约 2 次 `portBindable`（配置端口 1 次 + 必要时随机）+ 无需额外网络往返；adopt 路径仍 1 次 HTTP probe。
- **探活开销（detached 新增）**：周期性 `__DSH_BOOT__` probe，每次 ~ms 级；默认 30s 周期，每窗口每周期 1 次请求，开销可忽略；探活周期可配（`dsh.probeIntervalSec`）。
- 状态推送/标签：入 HTML 一次性字符串，无运行时开销。
- 崩溃退避总超时：≤90s 判失败，较现状最多 63s 退避 + 再等待可更早给 error；探活重拉同样受退避上限约束（不无限）。
- 内存：新增仅 1 个 net server 探针对象 + 1 个探活定时器，随用随关/随周期清理；detached stdout 落盘文件按日轮转（保留最近 N=3），防日志膨胀。

## 十、决策记录（ADR）

| # | 决策 | 理由 | 替代 | 影响 |
|---|---|---|---|---|
| ADR-1 | 端口判忙改为 `portBindable`（TCP bind） | 与真 bind 失败同一判定，消除 EADDRINUSE 假阴性 | HTTP-only（现状，已证伪） | 修问题 1 |
| ADR-2 | **detached 化 managed launch 为本迭代唯一基线**：托管 dsh = detached 独立进程；stop/restart 不杀（client 语义），仅「最后窗口 + 防误杀」才停 managed-own/extension | 用户评审明确直接上 detached；进程模型与手动 cmd 同构；**不做「既有子进程 + 停止语义改造」中间态**（其『未分离却『不杀』』自洽缺口随之消除） | v1 的「P0 中间态 + P1 后续」两档 | 修问题 2+4；本迭代基线；关闭原 F1 的中间态缺口 |
| ADR-3 | 顶部状态标签静态烘焙 ready 文案 | 与 iframe 静态同步，去脚本依赖 | 仅脚本更新（现状） | 修问题 3 |

| ADR-5 | **detached 化 managed launch 明确为本迭代基线（新 P0）**（不再作为「P1 后续」）；插件在 discover 失败时才代拉（与手动 cmd 同构） | 用户评审把 detached 从后续档提升为本轮实施目标 | 分两档推迟（v1，已否决） | 一次成型进程模型；代拉仅兜底 |
| ADR-6 | 崩溃重试降级到随机端口 + 总超时判失败；探活重拉复用同退避上限（不无限重启） | 防同端口死循环、防 npx 挂起无限等、防探活无限重拉 | 死磕同端口（现状）/无界探活 | 兜底 |
| ADR-7 | 注册表 `dsh` record = 重发现权威来源：`start()` 第 1 步对「record + pid 存活 + `__DSH_BOOT__`」re-adopt（残局重接管，F1）；`external` 最后窗口**不删记录**（known-external 保留，仅陈旧才清，F2）。detached 下异常退出（exit 钩子不触发）不影响独立常驻 dsh，re-adopt 使下一窗口无不可达孤儿 | 注册表权威重发现；外部非默认端口（3080 被占回落 random）清记录后无法从默认端口探知、不可达 | 窗口关了就删记录（现状，产生不可达孤儿 / 非默认 external 不可达） | 关闭 F1/F2；detached 基线自洽 |
| ADR-8 | 新增单一来源 `LOOPBACK_HOST` 常量（与 dsh `--host` 同源），`portBindable`/`probe`/url/`--host`/netstat 统一引用，去 `127.0.0.1` 字面量新增；**`URL_RE` 内 `127.0.0.1` 为既有字面量、与 `LOOPBACK_HOST` 同源，豁免（F4）不参与本次去硬编码**；CSP `frame-src http://127.0.0.1:*` 属安全约束保持隐式不变 | 去硬编码约束 | 各处字面量（现状） | 关闭 F3（F4 豁免边界） |

| ADR-9 | detached 下端口解析数据源改为**从日志文件回读**（F-PORT）：固定端口路径直接对该端口 `__DSH_BOOT__` probe、不解析；随机端口路径 tail 轮询 `logs\dsh-<ts>.log` 横幅，用单一 `resolvePortFromLog`（复用 `URL_RE`，读文件非 stdout）解析端口后 probe 确认；二者共用 `waitReady` | detached+重定向+unref 后 stdout 事件源消失，随机端口只能从日志横幅得知；保证「随机路径可解析且可 probe 确认」闭环；A/B 共用 `resolvePortFromLog` 去重 | 仍监听 stdout pipe（已随 detached 移除，不可行） | 闭合 F-PORT；P0-B / §十二 判据落点 |
| ADR-10 | **`dsh.updateRuntime` 为「显式强制重拉（force relaunch）」的受控例外（F-UPDATE）**：在该命令上经用户确认后，对 `managed-own` dsh 执行**受控 kill + 重新 managed launch**（npx 重新解析 latest）；对 `external`/已 adopt dsh **不 kill**，改为提示「版本更新需由手动 cmd 或受控重拉」 | P0-E 把 `dsh.restart` 改为 reconnect（不杀）后，`updateRuntime` 经 `executeCommand('dsh.restart')` 将无法更新版本；显式例外仅用于「用户主动确认升级」，与「stop/restart 不杀」不冲突 | 复用 `dsh.restart`（reconnect，无法更新版本，已否决） | 闭合 F-UPDATE；P0-E / 命令文案落点 |

> ADR 与 v1 差异说明：v1 的 ADR-2 需显式声明「P0 承诺收敛为不 kill + 记录保留、child 中间态残留缺口由 ADR-7 兜底」；**v2 直接 detached 化后，ADR-2 的重心转为「detached 独立进程为本迭代唯一基线」，无需再为 child 中间态做自洽修补**。v1 的 ADR-5 是「P1 后续 detached / 本迭代 P0 子进程」；**v2 的 ADR-5 明确为「本迭代 detached 基线」，不再有 P1 后续档**。ADR-7 语义保留（注册表权威重发现）但不再承担 child 中间态的孤儿修补（detached 下无该缺口）。

## 附：范围与影响（detached 化适配点）

detached 化是本迭代较大改动（进程模型 + 探活 + 关闭判定重构）。适配点评估：

| 组件 | 现况 | detached 适配 |
|---|---|---|
| `runtime.shutdownBookkeeping` | 直接 `treeKill(next.dsh.pid)`（最后窗口） | **需适配**：删除 dsh 的 `process` 引用（detached 无 child 可 dispose）；停止裁决改为按 `managedBy`：`managed-own`/`extension` & 最后窗口 & 三重防误杀 → taskkill + 清记录；`external` 不杀 + 保留 known-external 记录（仅陈旧才清）。pid 依据从 `this.process.pid ?? adoptedPid` 改为纯注册表 `next.dsh.pid`。 |
| `runtime.dshAlive`/`probe` | 现用于 adopt 前校活 | **需适配/复用**：新增周期探活（§6.4.2）复用 `probe()`/`isAlive()`；`stopped` 语义与 dsh 本体解耦；探活判死驱动 `ready→starting` 有界重拉。 |
| `runtime.waitForExternalStartup` | 轮询注册表 adopt | **保留（轻适配）**：仍轮询注册表；因 managed launch 是 detached，第二窗口首次启动可能与第一窗口并发——锁仲裁 + 注册表 adopt 关系不变；补 `managedBy` 沿用。 |
| `instance.ts` 注册表 `DshRecord` | `managedBy: 'extension' \| 'external'` | **需适配**：`managedBy` 扩 `'managed-own'`；pid 语义对 detached 仍记录（供 taskkill / 探活 / re-adopt），去 `this.process` 强依赖（detached 不再有 child 对象）。 |
| `dshProcess.ts` | 子进程监督 + 持有 child | **需适配（核心）**：detached launch（`unref`、不持有句柄）、文件日志、**端口解析数据源改为 `resolvePortFromLog`（F-PORT：固定端口直接 probe / 随机端口 tail 日志解析 + probe）**、崩溃退避改建为启动总超时 + 探活重拉（复用退避上限）。 |
| `extension.ts` | 命令直接杀 | **需适配**：stop/restart → disconnect/reconnect；文案「不关停 dsh」；`process.on('exit')` 保留但停止裁决按 managedBy。 |
| `webview.ts` | 顶部标签脚本环 | **需适配**：静态烘焙 `dsh · <url>`（无新字面量）。 |
| `scripts/sim.mjs` | 8 用例 | **需适配**：追加 detached 参数断言 / 探活 / 停止权 / re-adopt / known-external 用例；netstat/taskkill/真实 detach 相关建 SKIP。 |
| `paths.ts` | 数据目录/日志 | **适配**：暴露 `LOOPBACK_HOST` 常量；日志文件名支持 detached 落盘 `dsh-<ts>.log` 轮转。 |

**变更文件清单**：`src/{runtime,dshProcess,instance,extension,webview,paths}.ts` + `scripts/sim.mjs`（+ 新增 webview 单测文件，如 `test/webview.spec.ts` 或并入 sim）。`managedBy` 类型变更会连带 `instance.ts`/`runtime.ts`（一处联合类型 + 相关裁决分支）。

**分步说明（如判断超出单次迭代）**：detached 化目标不变，可拆为两步施工但**不得退回「非分离子进程 + 不杀」中间态**：
- 步骤 1（进程模型）：detached launch（`unref` + 文件日志 + 双保险端口解析）+ 注册表 `managedBy='managed-own'` + 关闭判定改 managedBy 裁决（此步后即可安全「不杀」）。
- 步骤 2（探活/重拉）：外部周期探活 + 有界重拉 + 顶部标签烘焙 + sim 用例补全。
> 两步都是 detached 基线的一部分，步骤 1 之后进程已是 detached 独立常驻，只是探活/重拉尚未就位（此时以启动总超时兜底）。两者均不引入 child-managed 中间态状态。
