## 一、目标/背景分析

0.1.18 部署轮声称 sim 无头回归 ALL PASS（490 PASS / 0 FAIL / 9 SKIP，exit 0）。QA 发布审计亲自三跑均未复现：一次 477 PASS / 13 FAIL / 9 SKIP（exit 1），两次以 `ERR_UNHANDLED_ERROR` 崩溃（exit 1）。用户随后在 DSH 沙箱外的普通 PowerShell 复跑，同样崩溃，且崩溃块与 QA 沙箱不同。三次（QA 沙箱）+ 一次（普通终端）失败模式互不相同，QA 按「无法核实 = FAIL」判 P3 FAIL 并回环架构师。

本文目标：用**一套**根因模型解释**全部**观察；给出修复清单（区分 sim 测试基础设施与产品代码）；给出修复后可执行的验收口径。本轮只做分析与方案设计，未修改任何 `scripts/sim.mjs` / `src/` 代码。

## 三、证据链

### 3.1 普通终端崩溃链（O4–O6，引 runtime.log 行号）

1. **mock 被产品逻辑真实 kill**：sim multi-window 块（sim.mjs L429）用 `makeRecord(mockPid, MOCK_PORT, 'extension')` 把 mock 注册为插件托管的 dsh；窗口 B 关闭时产品走"最后窗口停止 dsh"路径。runtime.log L6 显示校验通过（`verify holder={...} expected pid=17608`），L7 决定 kill，L8 记录清除。**产品行为本身正确**（src/runtime.ts L1331–1345：holder pid 与记录匹配才 kill，这是防误杀的保险门，代码注释即 "safe side"）。
2. **探测时机错位造成误判**：sim.mjs 的 `netstatUsable()`（L405–408）实际语义是「MOCK_PORT 端口上的持有者进程是否仍是 mock」，但它在 `shutdownBookkeeping()`（kill 已发起）**之后**才被调用（L446）。kill 成功 → 端口已无持有者 → 返回 false → 走 SKIP 分支（L450–455），把「mock 已被正确杀死」伪装成「netstat 不可用」。SKIP 文案里的 "sandbox" 是旧措辞残留——**普通终端也打出了这句**（O4），证明该文案与真实原因无关。
3. **死 pid 进 seed → 无法接管 → 真实启动**：P0-I-2/3 块（sim.mjs L478）复用同一个已死亡的 mockPid 去 seed `managedBy:"external"` 记录。runtime start() 第一步读到 `alive=false`（runtime.log L11）→ 不走接管 → 第二步探活也失败（L12）→ 落入 launchManaged（L14）。
4. **真实 spawn 穿透**：launchManaged 走 direct 模式（runtime.log L15 `launch mode = direct`），经 `DSH_NPX_ROOT` 注入口解析到 mock 布局里的 stub 包（L16–18），以 `node <bin.js> web --host ...` 形式 spawn（本探针实测 spawnCalls 第三条 argv 首三段即 `[bin.js, 'web', '--host']`，见 `probe-fupdate-stdout.txt` L9）。sim 的全局 spawn 路由（sim.mjs L164–171）把「argv 第 2 个 token 是 `web`」归类为 launch 类，但**只有 `captureLaunch === true` 时才拦截**（L192–194）；P0-I-2/3 块没有开启该开关 → 路由放行 → **真实 spawn 33 字节 stub**（O7 的 0 字节日志由 start() 常规创建——见 3.3，0 字节不代表真实进程写过内容；本块无任何 mock，穿透是确定性的）。
5. **stub 永不监听端口 → 6 × 90 秒耗尽**：fixed 端口 45678 探测失败（runtime.log L21）→ 降级随机端口（L22）→ 随机端口分支只认日志横幅（stub 不写日志，永远为空）→ 每次尝试跑满 90 秒 → 6 次耗尽（L21–62）→ `state: starting -> error`（L63）→ **emit('error')**。
6. **sim 对该 runtime 实例没有挂 'error' 监听** → Node 的 EventEmitter 对无人接收的 `error` 事件直接抛出 `ERR_UNHANDLED_ERROR` → **整个 sim 进程死亡**（sim-normal-terminal-utf8.log L25–28）。这个错误本应表现为一条 FAIL 断言，实际把整套件炸没了。

### 3.2 QA 沙箱三跑的分叉（O2、O3、O8）

本轮用只读探针直接复现了 QA run2/3 的现场（不改任何项目代码）：

**探针 1（复刻 F-UPDATE 块全 mock 组合）**：`.dsh/tmp/architect/rc0118/probe-fupdate.mjs`
- 装 sim F-UPDATE 同款三 mock（`DP.treeKill` 替换、`globalThis.fetch` 永远成功、`cp.spawn` 完全替换为返回裸假对象），seed managed-own 记录（死 pid 99999999，端口 3082），调 `forceRelaunchManaged()`。
- 实测结果（**stdout 原样留档于 `probe-fupdate-stdout.txt`，运行时间戳 2026-09-09T20:35:17+08:00，exit 0；以下数值与留档逐字一致**）：`result=PROBE-TIMEOUT-20s elapsed=20003ms state=starting fetchHits=0 emitted=0`——20 秒探针超时时 `forceRelaunchManaged()` 仍未返回（还在第一个 90 秒预算里）；**fetch 计数 = 0**（就绪探测从未执行）；spawn 三次调用**全部被 mock 拦截**（两条 `npm view` + 一次 direct launch `[bin.js, 'web', '--host']`，无真实子进程）。`emitted=0` 是因为探针自身挂了 `error` 监听且 20 秒 < 90 秒预算——emit('error') 要到 6 次尝试全部耗尽（约 9 分钟）才发生；sim 的 F-UPDATE 块没有这个监听，等到那一刻就是 `ERR_UNHANDLED_ERROR`。
- 探针 runtime.log 关键行（两份留痕逐行同构：QA 设计审计 r2 亲自核实的首次运行在 `probe-data-qa-verified-run1/logs/runtime.log`，2026-09-09 20:35 复跑在 `probe-data/logs/runtime.log`，关键行分别为 L4/L8）：`[dshResolver] npm view: child not observable (no event emitter); treating as failed run`（产品代码对 headless 假 child 有明确容忍，立即按失败收敛，不挂起）；**`launchManaged: port 3082 not bindable; falling back to random (ADR-1) (source=fallback-random, configured=3082, effective=0)`**。

**这条 "not bindable" 就是 QA run2/3 崩溃的直接机制**：

1. `resolveLaunchPort(3082)` 做真实 TCP 绑定测试（out/runtime.js L84–91），3082 不可绑定 → 降级**随机端口**（port=0）。
2. 随机端口路径的就绪等待（out/dshProcess.js L840–853）**只认日志横幅**（banner）：每次轮询先读 dsh 日志找 `dsh web: http://...:端口` 横幅行，有横幅才发起 HTTP 探测。spawn 全被 mock → 没有进程写日志 → 横幅永远不存在 → 循环里从不调用 HTTP 探测 → 这解释了探针里 **fetchHits = 0**（fetch mock 从未被触达）。
3. 90 秒预算耗尽 × 6 次 → `emit('error')`（out/runtime.js L515）→ sim 无监听 → `ERR_UNHANDLED_ERROR` 崩溃。与 run3 的崩溃栈（forceRelaunchManaged → launchManaged → emit）和失败文案（`did not expose a ready port within 90000ms`，随机端口分支专属文案）**逐字吻合**。
4. **QA 的 O8（"真实 spawn 33B stub bin.js"）是对留痕的误读**：`direct-node launch via resolver` 这行日志由 buildLaunch 打印（构建启动参数时的决策留痕），0 字节 dsh 日志由 start() 里 `fs.openSync(logFile, 'a')`（out/dshProcess.js L599）常规创建——**spawn 被 mock 时这两样同样存在**。探针实测 spawn 全被拦截、无真实子进程，但同样的留痕一样出现。QA 据此判定"真实 spawn"不成立；QA 按「无法核实 = FAIL」判 FAIL 的结论本身不受影响（三跑确实未复现 ALL PASS）。

**run2/3 崩溃的触发点因此是：3082 端口在 QA 沙箱内不可绑定，与 spawn/fetch mock 是否在位无关（前者为推断，标注于 2026-09-09 修订 1.1）。**该时点（17:27 / 17:44）的端口状态无人直接测量过；判定为推断的依据是排除法：① run2/3 崩溃表现为「随机端口横幅等待超时 ×6」且失败文案 `did not expose a ready port within 90000ms` 是随机端口分支专属文案——只有 `resolveLaunchPort(3082)` 绑定失败才会走该分支（探针 1 已实测该回退路径的完整留痕，见 `probe-data/logs/runtime.log` L8-9）；② QA run1（17:24）F-UPDATE 块 PASS（fetch mock 生效、秒过 ready）说明当时 3082 尚可绑定——3082 在 17:14→17:24 仍可绑定、17:27 崩溃，时间线上不可绑定状态恰好落在 run1 与 run2 之间。机制本身（3082 不可绑定 → fallback-random → 崩溃）已被探针 1 直接证实，属实测；「run2/3 当时 3082 不可绑定」这一时点归属是据失败模式反推的推断。

### 3.4 观察 O7：两个 dsh 日志为什么缺失

out/paths.js 的日志轮转是「**每次新建日志前，先保留最新 3 个旧文件、删除更旧的**」（`rotateDshLogs(dir, 3)`，每次 `managedDshLogFile()` 调用触发）。launchManaged 的 6 次尝试各建一个日志文件：

- attempt #1–#4 依次积累 4 个文件；
- attempt #5 新建前轮转：删除 #1，保留最近 3 个 + 新建；
- attempt #6 新建前轮转：删除 #2，保留 #3/#4/#5 + 新建 #6。

最终目录里恰好是 attempt #3–#6 共 4 个文件——**与实测完全吻合**（保留策略 = 3 旧 + 1 新 = 4）。0 字节是因为父进程只创建了追加句柄，被 spawn 的（真实或被 mock 的）子进程从未写入任何内容。

### 3.5 汇总：一套模型解释全部观察

| 根因 | 内容 | 解释的观察 |
|------|------|-----------|
| **A. sim 测试基础设施缺口（两处）** | A1 mock 生命周期无隔离：multi-window 块把 mock 注册为插件托管并真实 kill 后，后续块复用已死 mockPid；`netstatUsable()` 语义错位（在 kill 后探测、把「mock 已死」误报为「netstat 不可用」）；SKIP 文案残留 "sandbox" 字样 | O4、O5、O6（普通终端崩溃链） |

| **B. sim 对「配置端口可绑定」的环境假设在 DSH 沙箱不成立且随时间漂移**：部分端口 EACCES（Windows 保留段）、部分端口 EADDRINUSE（沙箱网络虚拟化保留，宿主视角不可见、随时间出现）。**对应修复项 F5（端口注入口，2026-09-09 修订 1.1 补）** | O1（部署轮端口环境恰好符合假设——推断标注见 §3.3）、O2（run1：3118/3132 已失效 → 3 源头 FAIL + 10 连锁）、O3（run2/3：3082 失效 → 崩溃）、O8（QA"真实 spawn"判断为误读） |

## 六、修复后验收口径（Q3 明确回答）

**前置条件（2026-09-09 修订 1.1 新增，缺此条件本节验收结论无效）**：§十一实施清单中的 **F5（PP-3-5①/PP-6-3①② 端口注入口）已落地**。理由：根因 B（沙箱回环端口绑定状态）随时间漂移——部署轮 17:14 全部通过、QA run1 于 17:24 出现 3 条源失败加 10 条连坐失败，正是同日不同时刻的反例；未做 F5 时，同一时窗内的 3 连跑全绿对端口环境稳定性没有证明力，可能得出假阴性验收结论。

**通过的充分必要条件**（缺一不可）：

1. **DSH 沙箱内（子代理执行）**：`node scripts/sim.mjs` 在**两个不同时段各连续 3 次**（两批开始时刻间隔 ≥ 30 分钟，共 6 次）全部 ALL PASS（490 PASS / 0 FAIL，exit 0）。分两批是为了覆盖端口环境随时间漂移——单时窗连跑已被证明不足（见前置条件理由）。SKIP 数允许波动：基线 9 ± 2，且 F5 落地后在端口漂移时段允许再新增最多 3 个 SKIP（PP-3-5①/PP-6-3①② 端口环境不满足）；每一项 SKIP 必须能对应到「真实环境缺失」（如 CIM/netstat 校验不可用）或「端口环境不满足」（F5 注入口判定），且文案与原因一致。
2. **用户普通终端（沙箱外）**：至少 1 次 ALL PASS，exit 0。该环境覆盖 QA/沙箱不具备的路径：netstat 可用 → last-window kill 真实发生 → 验证 F1 的隔离修复。
3. **无崩溃**：所有运行 exit code 为 0 或 1（1 仅允许来自 FAIL 断言计数），**不允许出现 `ERR_UNHANDLED_ERROR`**。修复后即使底层再遇端口漂移/mock 失效，表现也必须是「FAIL 断言」或「注明原因的 SKIP」而非进程崩溃。
4. **跨环境一致性**：同一产物在上述环境的结果差异只允许出现在 SKIP/非确定性时序类断言上，**不允许**出现「同一断言 A 环境 PASS、B 环境 FAIL」的行为分歧。PP-3-5①/PP-6-3①② 的端口敏感性已由 F5 在实现层前置处理（端口不可绑定 → 显式 SKIP 并注明原因），不再依赖验收失败后的补救。

**用户配合项**：修复 commit 落地后，请用户在普通 PowerShell 执行一次 `node scripts/sim.mjs > .dsh\tmp\sim-accept-normal.log 2>&1` 并回传汇总行与 exit code（不必多次；沙箱子代理负责两批 6 次口径，见条款 1）。可选加验：在普通终端执行 `node -e "require('net').createServer().listen(3082,'127.0.0.1',function(){console.log('3082 bindable');process.exit(0)}).on('error',e=>{console.log('3082 '+e.code);process.exit(0)})"`，确认普通终端 3082 可绑定（佐证端口漂移是沙箱特有，不阻塞验收）。

## 七、可行性分析（含探针数据）

## 八、可维护性分析

- F1–F5 落地后，sim 恢复「同一环境结果确定」的回归脚本属性（F5 同时消除对沙箱端口环境的时间敏感性）；后续 0.1.19+ 链的 QA 审计不再需要区分「伪造运行」与「环境漂移」。

- 建议在 `docs/README.md` 或术语变更记录中登记「非确定性」的正式口径（本文档第二节已定义），避免后续链复用模糊表述。

## 九、性能分析

## 十二、风险与不做的事

**风险**：
1. **沙箱端口状态继续漂移**：修复以「断言不依赖真实端口绑定」为原则（F1/F2/F4/F5 + 验收第 4 条）；已知的两个环境敏感断言（PP-3-5①/PP-6-3①②）由 F5 显式处理，若测试专家落地时发现其他块仍依赖真实绑定，需在评审时点名处理。

3. **sim 改动量**：5 项（F1–F5）均为测试基础设施修改，改动集中且相互独立；需 QA 复审防止新引入行为分歧（尤其 F4 方案二的全局拦截是否破坏个别需要真实子进程的既有断言——mock server/victim 走原始 import spawn，理论上不受影响；F5 的 SKIP 判定不得把「端口不可绑定」误报为其他原因，测试专家落地时逐块回归）。
