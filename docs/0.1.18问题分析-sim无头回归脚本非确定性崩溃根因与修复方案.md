## 一、目标/背景分析

0.1.18 部署轮声称 sim 无头回归 ALL PASS（490 PASS / 0 FAIL / 9 SKIP，exit 0）。QA 发布审计亲自三跑均未复现：一次 477 PASS / 13 FAIL / 9 SKIP（exit 1），两次以 `ERR_UNHANDLED_ERROR` 崩溃（exit 1）。用户随后在 DSH 沙箱外的普通 PowerShell 复跑，同样崩溃，且崩溃块与 QA 沙箱不同。三次（QA 沙箱）+ 一次（普通终端）失败模式互不相同，QA 按「无法核实 = FAIL」判 P3 FAIL 并回环架构师。

本文目标：用**一套**根因模型解释**全部**观察；给出修复清单（区分 sim 测试基础设施与产品代码）；给出修复后可执行的验收口径。本轮只做分析与方案设计，未修改任何 `scripts/sim.mjs` / `src/` 代码。

## 三、证据链

### 3.1 普通终端崩溃链（O4–O6，引 runtime.log 行号）

1. **mock 被产品逻辑真实 kill**：sim multi-window 块（sim.mjs L429）用 `makeRecord(mockPid, MOCK_PORT, 'extension')` 把 mock 注册为插件托管的 dsh；窗口 B 关闭时产品走"最后窗口停止 dsh"路径。runtime.log L6 显示校验通过（`verify holder={...} expected pid=17608`），L7 决定 kill，L8 记录清除。**产品行为本身正确**（src/runtime.ts L1331–1345：holder pid 与记录匹配才 kill，这是防误杀的保险门，代码注释即 "safe side"）。
2. **探测时机错位造成误判**：sim.mjs 的 `netstatUsable()`（L405–408）实际语义是「MOCK_PORT 端口上的持有者进程是否仍是 mock」，但它在 `shutdownBookkeeping()`（kill 已发起）**之后**才被调用（L446）。kill 成功 → 端口已无持有者 → 返回 false → 走 SKIP 分支（L450–455），把「mock 已被正确杀死」伪装成「netstat 不可用」。SKIP 文案里的 "sandbox" 是旧措辞残留——**普通终端也打出了这句**（O4），证明该文案与真实原因无关。
3. **死 pid 进 seed → 无法接管 → 真实启动**：P0-I-2/3 块（sim.mjs L478）复用同一个已死亡的 mockPid 去 seed `managedBy:"external"` 记录。runtime start() 第一步读到 `alive=false`（runtime.log L11）→ 不走接管 → 第二步探活也失败（L12）→ 落入 launchManaged（L14）。
4. **真实 spawn 穿透**：launchManaged 走 direct 模式（runtime.log L15 `launch mode = direct`），经 `DSH_NPX_ROOT` 注入口解析到 mock 布局里的 stub 包（L16–18），以 `node <bin.js> web --host ...` 形式 spawn（本probe实测 spawnCalls 第三条 argv 首三段即 `[bin.js, 'web', '--host']`）。sim 的全局 spawn 路由（sim.mjs L164–171）把「argv 第 2 个 token 是 `web`」归类为 launch 类，但**只有 `captureLaunch === true` 时才拦截**（L192–194）；P0-I-2/3 块没有开启该开关 → 路由放行 → **真实 spawn 33 字节 stub**（O7 的 0 字节日志由 start() 常规创建——见 3.3，0 字节不代表真实进程写过内容；本块无任何 mock，穿透是确定性的）。
5. **stub 永不监听端口 → 6 × 90 秒耗尽**：fixed 端口 45678 探测失败（runtime.log L21）→ 降级随机端口（L22）→ 随机端口分支只认日志横幅（stub 不写日志，永远为空）→ 每次尝试跑满 90 秒 → 6 次耗尽（L21–62）→ `state: starting -> error`（L63）→ **emit('error')**。
6. **sim 对该 runtime 实例没有挂 'error' 监听** → Node 的 EventEmitter 对无人接收的 `error` 事件直接抛出 `ERR_UNHANDLED_ERROR` → **整个 sim 进程死亡**（sim-normal-terminal-utf8.log L25–28）。这个错误本应表现为一条 FAIL 断言，实际把整套件炸没了。

### 3.2 QA 沙箱三跑的分叉（O2、O3、O8）

本轮用只读探针直接复现了 QA run2/3 的现场（不改任何项目代码）：

**探针 1（复刻 F-UPDATE 块全 mock 组合）**：`.dsh/tmp/architect/rc0118/probe-fupdate.mjs`
- 装 sim F-UPDATE 同款三 mock（`DP.treeKill` 替换、`globalThis.fetch` 永远成功、`cp.spawn` 完全替换为返回裸假对象），seed managed-own 记录（死 pid 99999999，端口 3082），调 `forceRelaunchManaged()`。
- 实测结果：**20 秒未返回**（还在第一个 90 秒预算里）；**fetch 计数 = 0**（就绪探测从未执行）；spawn 三次调用**全部被 mock 拦截**（两条 `npm view` + 一次 direct launch，无真实子进程）。
- 探针 runtime.log 关键行：`[dshResolver] npm view: child not observable (no event emitter); treating as failed run`（产品代码对 headless 假 child 有明确容忍，立即按失败收敛，不挂起）；**`launchManaged: port 3082 not bindable; falling back to random (ADR-1) (source=fallback-random, configured=3082, effective=0)`**。

**这条 "not bindable" 就是 QA run2/3 崩溃的直接机制**：

1. `resolveLaunchPort(3082)` 做真实 TCP 绑定测试（out/runtime.js L84–91），3082 不可绑定 → 降级**随机端口**（port=0）。
2. 随机端口路径的就绪等待（out/dshProcess.js L840–853）**只认日志横幅**（banner）：每次轮询先读 dsh 日志找 `dsh web: http://...:端口` 横幅行，有横幅才发起 HTTP 探测。spawn 全被 mock → 没有进程写日志 → 横幅永远不存在 → 循环里从不调用 HTTP 探测 → 这解释了探针里 **fetchHits = 0**（fetch mock 从未被触达）。
3. 90 秒预算耗尽 × 6 次 → `emit('error')`（out/runtime.js L515）→ sim 无监听 → `ERR_UNHANDLED_ERROR` 崩溃。与 run3 的崩溃栈（forceRelaunchManaged → launchManaged → emit）和失败文案（`did not expose a ready port within 90000ms`，随机端口分支专属文案）**逐字吻合**。
4. **QA 的 O8（"真实 spawn 33B stub bin.js"）是对留痕的误读**：`direct-node launch via resolver` 这行日志由 buildLaunch 打印（构建启动参数时的决策留痕），0 字节 dsh 日志由 start() 里 `fs.openSync(logFile, 'a')`（out/dshProcess.js L599）常规创建——**spawn 被 mock 时这两样同样存在**。探针实测 spawn 全被拦截、无真实子进程，但同样的留痕一样出现。QA 据此判定"真实 spawn"不成立；QA 按「无法核实 = FAIL」判 FAIL 的结论本身不受影响（三跑确实未复现 ALL PASS）。

**run2/3 崩溃的触发点因此是：3082 端口在 QA 沙箱内不可绑定，与 spawn/fetch mock 是否在位无关。**

### 3.3 端口绑定环境实测（O2 与 O3 的分水岭）

探针 2（`.dsh/tmp/architect/rc0118/probe-ports.mjs`）对 sim 用到的全部回环端口做绑定扫描（区分错误码）：

| 端口 | 结果 | 说明 |
|------|------|------|
| 3080 | FAIL: EADDRINUSE | 用户环境中正在运行的 dsh 主端口（pid 21928 @3080） |
| 3082 | FAIL: EADDRINUSE | **沙箱内可见占用，宿主视角无监听者**（见下） |
| 3118 / 3125 / 3132 / 3133 | FAIL: EACCES | Windows 保留端口段（系统级排除范围，边界随虚拟化栈状态漂移） |
| 3081 / 3083 / 3099–3117(除3118) / 3131 / 3135 / 3141–3146 | BINDABLE | — |
| 45678 / 45679 / 45691 / 45692 / 45693 | BINDABLE | mock 服务端口段全部正常 |

用宿主视角的 `Get-NetTCPConnection` 查 3082：**没有任何进程在监听**。即 EADDRINUSE 来自 DSH 沙箱的网络虚拟化层（对回环端口的映射/保留），沙箱内进程看得见拒绝、宿主看不见占用者。沙箱内无法进一步查明，如实记录。3082 在本轮探针时刻三次复测均为 EADDRINUSE（稳定）。

**端口环境是时间敏感的**（这解释了三跑结果互不相同）：

- **部署轮 17:14**：3118 / 3132 / 3082 当时均可绑定 → PP-3-5①、PP-6-3①②、F-UPDATE 全部走预期路径 → 490/0/9 ALL PASS（O1 成立，非伪造）。
- **QA run1 17:24**：3118 已 EACCES → PP-3-5① 断言 `snap35.port === 3118` 不成立（实际走随机端口落点）→ FAIL；3132 已 EACCES → PP-6-3 首轮载荷带的是 `--port 0` 而非断言的 `--port 3132`，且 trace 出现第二条 `not bindable` → PP-6-3①② FAIL；上述源头把 PP-3-5④ / PP-6-5 等 10 个「全族没有回归」聚合检查连锁拖挂。**3082 当时仍可绑定** → F-UPDATE 走固定端口探测 → fetch mock 生效 → 秒过 ready → PASS。整卷跑完，477/13/9，exit 1，不崩溃。
- **QA run2/3 17:27 / 17:44**：3082 变为 EADDRINUSE → F-UPDATE 崩溃（见 3.2）。

### 3.4 观察 O7：两个 dsh 日志为什么缺失

out/paths.js 的日志轮转是「**每次新建日志前，先保留最新 3 个旧文件、删除更旧的**」（`rotateDshLogs(dir, 3)`，每次 `managedDshLogFile()` 调用触发）。launchManaged 的 6 次尝试各建一个日志文件：

- attempt #1–#4 依次积累 4 个文件；
- attempt #5 新建前轮转：删除 #1，保留最近 3 个 + 新建；
- attempt #6 新建前轮转：删除 #2，保留 #3/#4/#5 + 新建 #6。

最终目录里恰好是 attempt #3–#6 共 4 个文件——**与实测完全吻合**（保留策略 = 3 旧 + 1 新 = 4）。0 字节是因为父进程只创建了追加句柄，被 spawn 的（真实或被 mock 的）子进程从未写入任何内容。

### 3.5 汇总：一套模型解释全部观察

| 根因 | 内容 | 解释的观察 |
|------|------|-----------|
| **A. sim 测试基础设施缺口（两处）** | A1 mock 生命周期无隔离：multi-window 块把 mock 注册为插件托管并真实 kill 后，后续块复用已死 mockPid；`netstatUsable()` 语义错位（在 kill 后探测、把「mock 已死」误报为「netstat 不可用」）；SKIP 文案残留 "sandbox" 字样 | O4、O5、O6（普通终端崩溃链） |
| | A2 spawn 拦截缺口：direct-node 启动的 argv（`[bin.js, 'web', ...]`）被路由归为 launch 类，但 `captureLaunch=false` 时放行 → 无块级 mock 的块会真实 spawn | O6 步骤 4 |
| | A3 sim 对启动失败的 runtime 不挂 `error` 监听：本应收敛为 FAIL 断言的错误把整个进程炸掉（O4、O3 共同机制） | O3、O4 |
| **B. sim 对「配置端口可绑定」的环境假设在 DSH 沙箱不成立且随时间漂移**：部分端口 EACCES（Windows 保留段）、部分端口 EADDRINUSE（沙箱网络虚拟化保留，宿主视角不可见、随时间出现） | O1（部署轮端口环境恰好符合假设）、O2（run1：3118/3132 已失效 → 3 源头 FAIL + 10 连锁）、O3（run2/3：3082 失效 → 崩溃）、O8（QA"真实 spawn"判断为误读） |
| **C. 产品代码真缺陷：扩展宿主不监听 runtime 的 `error` 事件** | src/runtime.ts 有 4 处 `emit('error')`（L496 / 585 / 872 / 1116），**src/extension.ts（真实扩展宿主）没有任何监听**。Node 对无人接收的 `error` 事件按未捕获异常抛出——生产环境里 detached 启动耗尽、会话失效等场景会**直接 crash 扩展宿主进程**（所有窗口的插件失效），比 sim 崩溃更严重。sim 崩溃只是该缺陷在无头脚本里的同型表现 | O3、O4 的共同崩溃机制 |

QA 归因的「mock 拦截存在运行间非确定性」应当修正为：**mock 拦截本身是确定的；不确定的是 DSH 沙箱的回环端口绑定状态（EACCES 段边界与 EADDRINUSE 保留随虚拟化栈状态漂移）**。部署专家未伪造运行：499 总断言与声称口径自洽，且每个数据点都有明确的端口环境解释。

## 四、系统设计视角（修复后的收敛形态）

```
修复前                                    修复后（目标态）
────────────────────────────────────    ────────────────────────────────────
multi-window 块真实 kill mock            块结束 → 显式恢复 mock 存活态（或后续块用独立 mock）
        ↓                                        ↓
netstatUsable() kill 后探测 → 误报       探测结果在停机仲裁前采样；语义改名
SKIP 文案 'netstat unavailable'          SKIP 文案中性化（仅真正环境缺失才 SKIP）
        ↓                                        ↓
P0-I-2/3 seed 已死 mockPid               接管族用例使用独立活 mock（隔离 pid/port）
        ↓                                        ↓
launchManaged → router 放行真实 spawn    headless 下 launch 类 spawn 默认拦截（全局无真实启动原则）
        ↓                                        ↓
emit('error') 无监听 → 进程死            sim 侧：newRuntime 统一挂 error 兜底 → 转断言
        ↓                                产品侧：extension.ts 挂 error 监听 → 日志 + 面板 error 态，不 crash
ERR_UNHANDLED_ERROR                      → 扩展宿主存活
```

## 五、修复清单（逐项方案 + 验收断言 + 目标角色）

### 5.1 sim 测试基础设施（【测试专家】为主，开发专家配合）

| 项 | 方案 | 验收断言 |
|----|------|---------|
| **F1 mock 生命周期隔离** | multi-window 块结束后显式恢复 mock 可用性（重新 `startMock(MOCK_PORT)` 并更新 `mockPid`，或后续块统一改用块内独立 mock 实例）；P0-I-2/3 块不再复用 multi-window 块的 `mockPid`，seed 独立活的 mock 记录 | 在 netstat **可用**的环境（普通终端）连续 3 次运行，multi-window kill 路径真实发生后，P0-I-2/3 块全部 PASS、不出现 launchManaged 真实 spawn |
| **F2 `netstatUsable` 语义拆分** | ① 改名（如 `mockPortHeld`）并在 `shutdownBookkeeping` 调用**前**保存探测结果；② 判定改双条件：`isAlive(mockPid) && resolvePortPid(MOCK_PORT)?.pid === mockPid`；③ SKIP 文案中性化：去掉 "sandbox" 字样，改为「宿主端口持有者校验不可用，无法裁决 last-window kill」，并注明「记录保留是 safe-side 保护行为」 | 普通终端运行不再出现含 "sandbox" 的 SKIP 文案；kill 真实发生时走 PASS 分支而非 SKIP；沙箱（校验不可用）走 SKIP 且文案与原因一致 |
| **F3 `error` 事件兜底（崩溃转断言）** | `newRuntime()` 工厂统一在创建后挂 `r.on('error', (msg) => { runtimeErrors.push({ windowPid, msg }) })`；关键块断言处显式检查 `runtimeErrors` 为空（或与预期错误一致） | 人为制造 6 次启动耗尽（如把注入口解析到不可启动的 stub 且断网）时，sim 输出 FAIL 断言并继续跑完整卷，进程 exit 码反映断言结果而非崩溃 |
| **F4 spawn 拦截缺口封堵（headless 无真实启动原则）** | 方向一（最小）：P0-I-2/3 及一切会走到 `launchManaged` 的块，自身临时置 `router.captureLaunch = true` 并提供 `onLaunch` 假 child（块结束在 finally 中还原）。方向二（根治）：`installSpawnRouter` 对 launch 类调用在未开启 captureLaunch 时也默认返回 fakeChild（而非 passthrough），并把「允许真实 spawn 的白名单」显式写成常量（仅 mock server / victim——两者本就走 import 的原始 spawn，不受影响）。推荐方向二 + 块级 try/finally 恢复，防止断言中途异常导致 mock 状态泄漏 | 在纯沙箱环境连续 3 次运行，全卷 `.sim-tmp/logs/` 不再出现 attempt 级 90 秒等待；无任何未被路由记录的真实 dsh 启动 |

### 5.3 验收把关（【QA】）

修复合入后按第六节口径验收；QA 审计需特别核对：三环境（沙箱子代理 ×3、用户普通终端 ×1 以上）全部 ALL PASS 且 exit 0；SKIP 清单中性化后逐项定性不再含行为分歧掩盖。

## 六、修复后验收口径（Q3 明确回答）

**通过的充分必要条件**（缺一不可）：

1. **DSH 沙箱内（子代理执行）**：`node scripts/sim.mjs` **连续 3 次**全部 ALL PASS（490 PASS / 0 FAIL，exit 0）。SKIP 数允许在 9 ± 2 内波动，但每一项 SKIP 必须能对应到「真实环境缺失」（如 CIM/netstat 校验不可用），且文案与原因一致。
2. **用户普通终端（沙箱外）**：至少 1 次 ALL PASS，exit 0。该环境覆盖 QA/沙箱不具备的路径：netstat 可用 → last-window kill 真实发生 → 验证 F1 的隔离修复。
3. **无崩溃**：所有运行 exit code 为 0 或 1（1 仅允许来自 FAIL 断言计数），**不允许出现 `ERR_UNHANDLED_ERROR`**。修复后即使底层再遇端口漂移/mock 失效，表现也必须是「FAIL 断言」而非进程崩溃。
4. **跨环境一致性**：同一产物在上述环境的结果差异只允许出现在 SKIP/非确定性时序类断言上，**不允许**出现「同一断言 A 环境 PASS、B 环境 FAIL」的行为分歧（PP-3-5①/PP-6-3①② 修复后应对端口环境不敏感——若做不到，须将该断言的环境敏感部分改为注入口注入，而不是依赖真实端口绑定）。

**用户配合项**：修复 commit 落地后，请用户在普通 PowerShell 执行一次 `node scripts/sim.mjs > .dsh\tmp\sim-accept-normal.log 2>&1` 并回传汇总行与 exit code（不必 3 次；沙箱子代理负责 3 次口径）。可选加验：在普通终端执行 `node -e "require('net').createServer().listen(3082,'127.0.0.1',function(){console.log('3082 bindable');process.exit(0)}).on('error',e=>{console.log('3082 '+e.code);process.exit(0)})"`，确认普通终端 3082 可绑定（佐证端口漂移是沙箱特有，不阻塞验收）。

## 七、可行性分析（含探针数据）

- **探针数据**：F-UPDATE 复刻探针 20 秒内稳定复现「3082 not bindable → 随机端口分支 → probe 不执行 → 预算空转」；端口扫描一表定位 4 个 EACCES 段端口与 2 个 EADDRINUSE 端口。探针脚本已留存（见前置参考），QA/测试专家可直接复跑取证。
- **修复可行性**：F1–F4 全部为 sim 局部改造（生命周期、探测时机、事件兜底、路由开关），不触碰产品行为矩阵；产品侧仅 extension.ts 一处事件监听，改动面小。技术可行。
- **资源**：测试专家修 sim 约 1 轮；开发专家改 extension.ts 约 10 行内；QA 验收 4 次运行（沙箱 3 + 用户 1）。时间可行。

## 八、可维护性分析

- F1–F4 落地后，sim 恢复「同一环境结果确定」的回归脚本属性；后续 0.1.19+ 链的 QA 审计不再需要区分「伪造运行」与「环境漂移」。
- `netstatUsable` 改名与文案中性化消除长期误导源（本次 QA 判 FAIL 的复核成本有一部分来自该文案误导）。
- extension.ts 的 error 兜底同时提高生产健壮性（上游 dsh 启动耗尽/会话失效不再拖垮扩展宿主），属于长期收益。
- 建议在 `docs/README.md` 或术语变更记录中登记「非确定性」的正式口径（本文档第二节已定义），避免后续链复用模糊表述。

## 九、性能分析

- 修复不改变产品启动/重试预算（90 秒 × 6 次、退避 1/2/4/8/16/32 秒），无性能影响面。
- sim 修复后单卷运行时长仍由预算型断言主导（正常约 7–10 分钟），端口环境不再造成 9.5 分钟级崩溃挂起（F-UPDATE 崩溃路径消除）。

## 十二、风险与不做的事

**风险**：
1. **沙箱端口状态继续漂移**：修复以「断言不依赖真实端口绑定」为原则（F1/F2/F4 + 验收第 4 条）；若仍有块依赖真实绑定，需在评审时点名处理。
2. **普通终端 3082 占用未实测**：沙箱内宿主视角不可见，本轮无法核实 3082 的 EADDRINUSE 在宿主上是否同样存在；已给出用户侧可选验证命令，不影响主验收路径（修复后 sim 不再依赖 3082 可绑定）。
3. **sim 改动量**：4 项均为测试基础设施修改，改动集中且相互独立；需 QA 复审防止新引入行为分歧（尤其 F4 方案二的全局拦截是否破坏个别需要真实子进程的既有断言——mock server/victim 走原始 import spawn，理论上不受影响，测试专家落地时逐块回归）。

**不做的事**：
- 不调整产品 90 秒 × 6 次重试预算与退避策略（产品 ADR 决策，与本崩溃无因果）。
- 不在沙箱内复跑完整 sim（自删现场 + 时间成本，证据已充分）。
- 不改 `src/` 启动/接管/仲裁逻辑（唯一产品改动 = P1 事件监听兜底）。
- 不判定部署专家伪造（端口环境解释完全覆盖声称与复现差异；QA 判 FAIL 的依据「无法核实」仍然成立并已被发布审计如实记录）。
- 不直连 ssh/scp/sftp；不操作 main/master；不 push；不 npm view/install；不写真实 npx 缓存。
