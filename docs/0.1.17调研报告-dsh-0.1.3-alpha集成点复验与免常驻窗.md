## 一、目标/背景分析

1. **直接动因（用户提问，最高优先级）**：上游 0.1.3-alpha.1 发布说明称「Windows 上的本地非终端子进程不再弹出控制台窗口」。本项目 `dsh.consoleVisible=false`（完全隐藏）形态存在已知的「闪现窗口问题取舍」，package.json 描述写明「上游修复 windowsHide 后可切回」。需回答：该修复能否支撑**无常驻窗口终态**（无常驻窗口 + 零闪窗），以及默认值/实现如何调整。
2. **常规动因**：上游连发两个 alpha 版本，需按 8 个集成点框架复验对扩展的影响，筛出提升点与适配点，维持「no-adaptation 结论」或给出适配设计。
3. 背景因果链（0.1.6 文档 v2.4 定案，本轮复核仍成立）：dsh 0.1.1-rc.2 时代 `dsh-subprocess-local` 的 `spawnSubprocess` 与两处 `taskkill` 均无 `windowsHide`（37 个派生点仅 3 处带），父进程无（可见）控制台时每个工具子进程新建可见控制台 → 闪现窗口+抢焦点 → ADR-20/21 以「常驻可见控制台」（`consoleVisible=true`，默认值 true，用户裁决 2026-08-29/08-31）结构性掩盖，等待上游修复切回。

## 三、系统技术选型及设计

### 3.1 无常驻窗口修复的机制与覆盖（问题 2a 答案）

**落地提交**：`cc8099dc5f`（fix(subprocess): hide Windows child windows）+ `a05b5fbe79`（hide Windows cleanup helpers），经 `df07f37827`（Merge PR #3516 `turtle/issue-2390-windows-hide-subprocess`，issue #2390）进入 alpha.1 release 树（合并于 2026-09-04 11:52 +0800，早于 release 提交 15:38）。

**机制**（决策文档 `.agents/notes/implemented/bug-fix/2026-09-03-hidden-windows-subprocess-windows.zh.md` 全文已读 + diff 逐行）：
- `packages/subprocess/subprocess-local/src/spawn.ts`：`spawnSubprocess` 主 spawn 增加 `windowsHide: platform === 'win32'`（alpha.1 树 :387）；
- 同文件 `taskkillProcessTree`（:305 区域）与 `windows-inspector.ts taskkillTree`（:150）两处 `spawnSync('taskkill', …)` 增加 `windowsHide: true`——决策文档明确说明「只隐藏主子进程」被否决的理由：取消/超时升级/终端拆卸/宿主退出清理仍会启动 taskkill 闪现窗口；
- 语义强度：调用方**不可选择退出**（provider 统一决定）；`windowsHide` 同时隐藏「遵循 Windows 进程启动可见性设置的 GUI 窗口」；终端（PTY）路径明确保持 PTY 自有可见性行为。

**覆盖范围结论（v2 按路径分述）**：
- **已修（alpha.1 起）**：`spawnSubprocess` 主通道子进程（dsh 工具执行 bash/pwsh/rg/node 等）+ Windows 树终止 taskkill×2。这正是扩展侧闪现窗口的两大来源（0.1.6 文档 E-POP 取证：`spawnSubprocess`、taskkill L104/L744）。实测效果：工具子进程持**新建的 headless console**（无窗口，CREATE_NO_WINDOW 语义，r2 探针 M0-hide/M3-hide 实测）——零闪窗。**（r3 实机复证：三处 windowsHide 锚点在实机 alpha.2 安装树逐点定位 `runner-launch-COYGu0Dl.js:140/851/1146`，与源码 `e379fa8bdd` 一致；F 变体直调实装 `spawnSubprocess` 代码本体从无 console 的 DIRECT mid 派生 → 目标自持 headless console（visible=false，consoleProcs 仅自己）= 零可见窗，产物级动态复证。）**
- **alpha.2 引入的 runner 路径回归（v2 新增判定，r3 产物级实证）**：native containment（PR #2825）使 Windows ordinary 命令默认改走 windows-job runner（`windows-job.ts` spawn 仅 `{cwd, env, stdio}`，**无 windowsHide 无 detached**——实机安装树 `lib/index.js:499-507` 逐字实证）；runner 是 node console 程序（实机 `spawnRunnerInvocation()` → `[process.execPath, …/dsh-subprocess-local/lib/runner.js]`，runner.js 13,001B 实物已就位），从完全无 console 的 dsh spawn 无选项 → **新建可见 console = 每工具调用弹一窗**（r2 探针 M3/M3r 两轮实测，QA 独立复现一致；**r3 实机复证**：无 console mid + 无选项子 = 新建可见 console，M3 真机 `console=true visible=true consoleProcs=[自己]`）。Job 目标（`win32-process` `CREATE_SUSPENDED | CREATE_UNICODE_ENVIRONMENT`，无 CREATE_NO_WINDOW）继承 runner 可见 console。koffi 为 subprocess-local 正式依赖且发布含 win32 预编译二进制（**r3 实物升级**：实机安装树 `@koromix/koffi-win32-x64@3.2.1\win32_x64\koffi.node` 1,036,800B 实物已就位，v2「npm pack 实物 + 推断」注记删除）→ 该路径**默认生效**。**master HEAD（alpha.2 后 133 提交）两文件零 diff、无修复提交 → 回归未修**。（r3 补充：runner 进程链在本会话沙箱内受 named-pipe 边界阻断无法实机进程级直证，EPERM 边界经 10 组对照矩阵特征化，见 §四.2。）

### 3.2 对照扩展 spawn 链的两形态判定（问题 2b 答案，v2 全节重写）

扩展链（src/dshProcess.ts:704-742）：`consoleVisible=true` = START 家族（`cmd.exe /c start` 或 conhost，常驻可见窗）；`consoleVisible=false` = DIRECT：`spawn(node bin.js …, { detached: true, windowsHide: true, stdio: [ignore, fd, fd] })`。

**窗口探针（v2 重做）**：方法 = 两级 spawn 链（主进程 → mid → 孙）+ PowerShell P/Invoke 自报 `GetConsoleWindow` / `IsWindowVisible` / `GetConsoleProcessList`，以孙的 consoleprocs 进程列表**含不含祖先 pid** 做「继承 vs 新建」硬判别（QA `probe-qa-window-v3.mjs` 方法，r2 探针脚本 `probe-r2-window.mjs` 扩展为 5 变体矩阵）。原始输出全部落盘 `.dsh/tmp/architect/r2/`，汇总见 `r2-result.txt`，语义矩阵见 `verdict-matrix.md`：

- **B（dsh 形态 mid 自身，detached+windowsHide）**：**完全无 console**。判据 = M3 组无选项孙实测 `console=True visible=True` 且 `consoleprocs=1 ids=<仅孙自己>`——孙新建 console 而非继承，反证 mid 无任何 console 可给；M3r 组（stdio 改文件重定向 = 扩展 DIRECT 字节级同构）结果一致。**v1 的「dsh 持有不可见控制台（CREATE_NO_WINDOW 落地）」为误判**：DETACHED_PROCESS 与 CREATE_NO_WINDOW 同传时前者生效（不继承也不新建 console）。
- **C1（无 windowsHide 孙 = alpha.2 native runner 形态）**：`console=True visible=True`、`consoleprocs=1`（M3/M3r 两轮一致）= **新建可见 console = 弹窗**。v1 的「继承不可见控制台，不弹窗」**不成立**。
- **C2（windowsHide 孙 = alpha.1 修复形态）**：`console=False`（M0-hide/M3-hide 多轮一致）= **不弹窗**。v2 精确化表述：该孙附着的是**自持新建的 headless console**（无窗口；增强判别 `headless-procs=1` 只含自己——不是「完全无控制台」，而是「无窗口的控制台」，对用户可见效果为零窗口）。
- **判别器有效性对照（QA D4 要求）**：P0/M0 组实测「有（继承的）不可见 console 的宿主 → 无选项子**继承**不新建」：`console=True visible=False`、`consoleprocs≥2` 且 ids 含父 pid（P0-mainenv-grandchild.txt / M0-grandchild-noOpt.txt）——判别器可靠。
- **libuv 标志组合语义（M 矩阵补全）**：`{}` → 继承父 console（父无则新建**可见**）；`{detached}` → 完全无 console（M1 孙 procs=1 反证）；`{windowsHide}` → headless console（无窗口；**可被无选项子继承**——M2 组孙 `headless-procs=2` 含 mid pid；且 windowsHide 子不继承父窗口 console，自建 headless）；`{detached+windowsHide}` → DETACHED_PROCESS 生效 = 完全无 console（dsh 形态）。依据：libuv `UV_PROCESS_WINDOWS_HIDE` 覆盖 console 隐藏（[libuv commit b21c1f9](https://github.com/libuv/libuv/commit/b21c1f900c55572917d64c5e208c3eb8850ffd18)、[libuv 文档](https://docs.libuv.org/en/v1.x/process.html)）+ 本轮实测；libuv 源码逐行核对未完成（GitHub raw 经代理不可达，如实标注），判定以实测为准。

**实机探针补证（r3，扩展 DIRECT 同构 mid = detached+windowsHide 无 console；判别方法与 r2 一致；原始 JSON 全录 `.dsh/tmp/architect/r3/`）**：
- **M3-实机**（无 console mid + 无选项 node spawn pwsh 目标）：`console=true, visible=true, consoleProcs=[自己]` → **新建可见 console = 弹窗**——r2 M3/C1 语义在真实硬件上复现（即 alpha.2 runner 在隐藏形态的 console 行为语义同构）。
- **F-实机（产物级）**（直调实机安装树 `spawnSubprocess` 代码本体，windowsHide 主通道）：`console=true, visible=false, consoleProcs=[自己]` → **自持新建 headless console = 零可见窗**——r2 C2 语义从「源码+合成」升为「产物实机动态验证」。
- **活实例旁证**（只读探针自报，继承实机 harness console）：`GetConsoleProcessList` = 8 进程同 console，**含实机 dsh 主进程 40256** 与工具进程，console visible=false → 终端形态下 dsh 与其工具子**共享同一 console**（runner 无 hide 标志 spawn → 继承，不新建）。
- **用户自述观测（R3 证据级，与探针实测分列）**：用户实机 alpha.2 实例从 Windows Terminal 以 npx 手动启动（非扩展拉起），日常**无窗口闪出**；并反馈「时不时看到闪现窗口，与本链可见 console 探针派生时段吻合」（本轮探针副作用共 3 次，短命进程毫秒级退出，属方法固有副作用）——待 r3 结束后用户确认闪现窗口是否消失，可作「探针停即闪现窗口停」的旁证。该观测与机制自洽：终端形态 dsh 持有终端 console → runner 子继承同一 console 不新建窗；**闪现窗口回归仅在 dsh 自身无 console 的形态（扩展 DIRECT）下显现**。

判定（v2，r3 实机数据全部同向，无改判）：
- **`consoleVisible=false` + dsh = 0.1.3-alpha.1（仅此版本）**：闪现窗口的问题被结构性消除——工具子全部走 `spawnSubprocess` windowsHide → 自持 headless console（无窗口）。**无常驻窗口零闪窗承诺仅对此版本成立**。**（r3 补注：alpha.1 从未发布 npm——registry 全量版本列表无此版本 + 点查 E404 + 阳性对照成功，见 §四.3——该承诺版本在 npm 安装通道不可达，见 §3.3。）**
- **`consoleVisible=false` + dsh ≥ 0.1.3-alpha.2**：**弹窗回归**。ordinary 命令默认走 windows-job runner（koffi 正式依赖 + 发布含 win32 预编译二进制 `@koromix/koffi-win32-x64`，`probeWindowsJob()` 默认成功；r2 实物验证），runner 从无 console 的 dsh 无选项 spawn → 新建可见 console，每工具调用一窗（频率与 0.1.6 时代相当）；Job 目标继承 runner 可见 console。master HEAD 未修（见 §3.1）。koffi 加载失败等 fallback 才回落 alpha.1 行为（不可控，不作为承诺）。
- **`consoleVisible=true` 常驻形态**：两版均无弹窗。alpha.1 起工具子从「共享常驻可见控制台」变为「自持 headless console」（不写入常驻控制台窗口）；alpha.2 runner 从 dsh（**有可见 console**）无选项 spawn → **继承可见 console**（M0 判别器背书），Job 目标再继承 runner console——不新建窗。可观察差异 = 常驻控制台窗口内不再出现 msys `fatal error … couldn't create signal pipe` 类 CONOUT$ 直写噪声（0.1.6 文档 §3.12 P-PIPE 记录的现象面消失）；ADR-27 信息头与「关窗=停止」语义不受影响。**沙箱路径不受影响**：`sandbox-windows-acl` 走自有 Koffi CreateProcess（src/index.ts:27 明文 console 隔离因 0xC0000142 刻意缺席），不经 spawnSubprocess，无 0xC0000142 回归风险。
- **附带红利（alpha.2，非代码改动）**：native containment（PR #2825）使 Windows 普通命令进入 runner 独占的 kill-on-close Job——dsh 退出（含「关窗即停」）时 Job handle 关闭，**逃逸后代（setsid/重父化/长存活）被收容终止**；「关窗即停 dsh」从「杀主进程树」增强为「杀 managed range 全集」。**该红利仅在常驻形态下与零弹窗并存；隐藏形态下被 runner 弹窗回归抵消**（v2 修订：v1 未披露此张力）。

### 3.3 生效版本阈值与扩展侧设计（问题 2c 答案，v2 改为版本区间语义）

- **v1 的单一阈值 = `0.1.3-alpha.1` 已被证伪**：alpha.2 不是 alpha.1 的超集改进——native containment（PR #2825）引入的 runner 形态使 windowsHide 修复对 ordinary 命令失效（§3.2 判定）。
- **v2 阈值语义 = 版本区间**（沿袭 0.1.14 ADR-30 版本阈值模式 + semver 预发布感知比较，src/dshProcess.ts:471 + :484-535）：
  - **`WINDOWSAFE_MIN_VERSION = '0.1.3-alpha.1'`**（零闪窗形态下界，进入即无闪现窗口）；
  - **`WINDOWSAFE_REGRESSION_MIN_VERSION = '0.1.3-alpha.2'`**（runner 路径弹窗回归上界起点；上游修复版发布后由用户评审裁决将其改置——常量机制预留演进路径）；
  - 判定三段：运行时 < alpha.1 / ∈ [alpha.1, alpha.2) / ≥ alpha.2（见降级行为）。
- **降级行为（v2 三段）**：
  - < `0.1.3-alpha.1` 且用户设 `consoleVisible=false` → 维持现状（完全隐藏 + 已知的闪现窗口问题取舍，与 0.1.7-0.1.16 行为一致，rlog 提示一次「运行时 < 0.1.3-alpha.1，隐藏形态存在上游闪现窗口的取舍」）；
  - ∈ [alpha.1, alpha.2) → 零闪窗承诺版本区间，无提示（或 rlog 信息级一次性确认）；
  - ≥ `0.1.3-alpha.2` → rlog **警告一次**「dsh ≥ 0.1.3-alpha.2 的 native runner 在隐藏形态存在上游弹窗回归（PR #2825 引入，上游 master 未修），零闪窗仅对 0.1.3-alpha.1 成立——**该版本未发布 npm，建议等待上游修复版**」，不阻塞启动。（r3 修正：原「建议暂留 0.1.3-alpha.1」不可执行，已改。）
- **无常驻窗口终态在当前 npm 可安装版本上不可达成（r3 改判：v2 的「区间内版本」在 npm 上不存在）**：registry 全量版本列表（16 版本）中 0.1.3 系列**仅 0.1.3-alpha.2**——alpha.1 从未发布 npm（§四.3），承诺版本区间 [alpha.1, alpha.2) ∩ npm 可安装集 = **∅**。达成条件（交用户评审）：① **等上游修复 runner spawn 的 windowsHide**（HEAD 未修，反馈材料已备 `r2/upstream-issue-draft.md`，不代发；修复版发布后区间上界常量改回、重验、解除回归阈值——**主路径**）；② **非 npm 渠道安装 alpha.1**（从源码 `ed67c22496` 本地 pnpm 构建，或从 git/tarball 渠道安装）——成本中等偏高（monorepo 全量构建 + 手工安装 + 产物非 npm 官方物的标注义务），且 resolver 当前按 channel dist-tag 解析、无版本 pin 能力，**列为待评审选项，不作为 A1 链前置**；③ 上游修复后重验并解除回归阈值（与①同路径的收尾动作）。**文案红线**：一切描述/发布说明不得出现「升级到 0.1.3-alpha.1 即可」类不可执行指引。
- **默认值策略（交用户评审二选一）**：
  - 方案甲（推荐，v2 维持、r3 维持）：`consoleVisible` 默认值**维持 true 不变**，仅更新 package.json 描述（改述两形态语义与 alpha.2 回归事实 + 「npm 可安装版本中暂无零闪窗承诺版本」）+ 落版本区间判定 + 真机验收（**r3 重定判据，见 §九 #3**：alpha.2 常驻形态零弹窗 + 隐藏形态回归行为与文档一致 + 检查警告生效；隐藏形态零闪窗真机验收移交上游修复版）通过后，由用户自行切 false。理由：真机验收在先、默认值切换在后，风险最小；且当前 alpha 通道已到 alpha.2，未修复前默认切换会把回归暴露给所有用户。
  - 方案乙：验收通过后直接把默认值切换为 false。代价：未真机验收前有回归暴露范围（含实验性 Python 路径、用户自定义 command 混用等长尾）；且需先解决「alpha 通道用户拿到的是 alpha.2（有回归）」的版本错位问题。

## 四、可行性分析（含探针数据，v2 重写）

1. **源码可行性**：修复机制 = 单选项（windowsHide）三处落地，无 API/协议/进程形态破坏（见 §3.1）；**但 alpha.2 起 native runner（`windows-job.ts` spawn 无 windowsHide）在 ordinary 命令上使该修复失效**——runner 从无 console 的 dsh spawn 无选项 node（console 程序）→ 新建可见 console（r2 实测，QA 独立复现一致）。
2. **窗口探针数据（v2，五轮迭代最终轮为准；脚本+原始输出全录 `.dsh/tmp/architect/r2/`，判别方法 = 两级 spawn 链 + `GetConsoleProcessList` 继承/新建判别）**：

   - `G1`（宿主对照语义）：「有不可见 console 的宿主 → 无选项子继承不新建」由 P0 与 M0 双证（孙 `consoleprocs≥2` 含父 pid）；host-g1 附加发现：CREATE_NO_WINDOW 链的 headless console 跨层可继承（`headless-procs=3` 同集）；
   - `B`（dsh 形态 mid = detached+windowsHide，M3/M3r）：**完全无 console**——无选项孙 `consoleprocs=1` 只含自己 = 新建，反证 mid 无 console；
   - `C1`（无 windowsHide 孙 = alpha.2 runner 形态，M3/M3r 两轮）：`console=True visible=True`、`consoleprocs=1` → **新建可见 console = 弹窗**；

3. **发布范围可行性（r3 重算，含关键改判）**：

   - **零闪窗承诺成立情况对照表重算（npm 可安装版本 × 两形态）**：≤0.1.2-alpha.5 隐藏形态 = 闪现窗口（无 windowsHide 修复）；0.1.3-alpha.1 = 无闪现窗口但 **npm 无此版本**（仅 git 提交 ed67c22496 / tarball 可装）；0.1.3-alpha.2 隐藏形态 = runner 回归弹窗。**⇒ v2 承诺版本区间 [alpha.1, alpha.2) 在 npm 可安装版本上为空集 ∅**——v2 验收判据 #3「pin alpha.1」不可执行，已重定（§九 #3）；一切文案不得出现「升级到 alpha.1 即可」类不可执行指引。
   - dist-tags 实测 alpha 通道已指向 `0.1.3-alpha.2`——**恰为回归版本**：扩展 alpha 通道用户经既有 ADR-12 原地刷新吃到的将是带 runner 弹窗回归的版本（v1 正向表述的改变维持）。
   - koffi 发布链（**r3 升级：推断 → 实机实证**）：实机安装树 `@deepseek-ai/dsh-subprocess-local@0.1.3-alpha.2` deps = `koffi ^3.1.0 / node-pty 1.2.0-beta.15 / dsh-win32-process ^0.1.3-alpha.2`；`@koromix/koffi-win32-x64@3.2.1\win32_x64\koffi.node` **1,036,800B 实物已就位** → runner 默认生效条件实机齐备（v2「npm pack 实物 + 推断」注记删除）。
   - npx 缓存清点（**r3 刷新，v2 数据已过时**）：本机 4 个 hash 目录 = **0.1.3-alpha.2（实机，mtime 2026-09-08 17:53）** / 0.1.1-rc.2×2 / 0.1.0-rc.7；v2 所记 0.1.2-alpha.5 已被用户升级清除。resolver（alpha 通道，V=0.1.3-alpha.2）将命中 alpha.2 目录（mode=steady）——扩展吃到的就是回归版本。
4. **风险清单（r3 更新）**：① **alpha.2 runner 弹窗回归（主风险，实机条件齐备）**——当前 alpha dist-tag 即 alpha.2，扩展原地刷新即暴露；master HEAD 未修；上游修复时间不可控；**r3 补强：实机安装树确认 runner 默认生效条件全部已就位（koffi.node 实物 + probeWindowsJob 选择链 + runner spawn 无 hide 选项代码实证），风险从「推断」升「实证」**；② **零闪窗承诺版本 npm 不可达（r3 新增，文案面主风险）**——alpha.1 未发布 npm，若文案/发布说明出现「升级 alpha.1」类指引即为误导，已按红线修正（§3.3/§九 #5）；③ koffi 原生依赖随 alpha 包分发——首次冷缓存下载耗时/体积上升；koffi 加载失败时上游降级 fallback（一次 warning + 既有较弱保证），功能不破——**注意 fallback 恰好回落到零闪窗形态，但不可作为承诺依赖**；④ 实验性 Python 运行时路径未修（detached+无 windowsHide），启用时无常驻窗口形态仍有弹窗可能——标注边界，不阻塞；⑤ native containment 的 runner+target 双进程形态使每次 spawn 多一个进程（见 §六）；⑥ ~~版本 pin 到 alpha.1 的用户停留在旧版~~（**r3 删除**：npm 上无 alpha.1 可 pin，该权衡项不成立；改为「非 npm 渠道手工装 alpha.1 的用户停留在旧版」——待评审选项②的附带动机，非现状风险）。
5. **结论**：**条件性可行（r3 收窄）**。无常驻窗口零闪窗机制在 dsh = **0.1.3-alpha.1** 成立（源码 + r2 探针 + **r3 产物实机动态验证（F 变体）** 三证）；但该版本**未发布 npm**，alpha.2（npm 现 alpha dist-tag）起 runner 路径回归，**npm 可安装版本上零闪窗承诺集为空**——终态需上游修复（主路径）或非 npm 渠道安装 alpha.1（待评审）后才可推进；真机 GUI 验收按 §九 #3 重定判据执行（alpha.2 常驻零弹窗 + 隐藏形态回归行为与文档一致 + 检查警告生效）。

## 五、可维护性分析

1. 版本阈值常量与既有 `TOKEN_AUTH_MIN_VERSION` 同址同模式（dshProcess.ts），单一判定点，升级即改常量；语义命名区分「token 契约阈值」与「免闪现窗口阈值」，避免阈值语义粘连（语义分离纪律）。
2. `consoleVisible` 语义不扩（仍二元），只更新描述文案与检查提示；不引入第三态，注册表/UI 语义保持二值（沿 ADR-21 先例）。
3. 上游 alpha.2 将连接恢复参数收敛为 `recovery-config.ts` 单一 schema——若未来扩展需要感知，读点集中；本轮无需跟进。
4. 决策文档（上游 `.agents/notes`）与 release commit 双锚使未来复验可重放：锚点 = release 提交号（tag 缺失时），重放命令与全部探针输出固化于 `.dsh/tmp/architect/r2/`（v2 起过程记录自含该目录，见 provenance 事故记录）；**r3 起真机取证（安装树锚点 grep 命令 + 探针脚本 + 原始 JSON + npm registry 原始输出）固化于 `.dsh/tmp/architect/r3/`（README 含证据分级索引，R1 实物/R2 探针/R3 用户自述/R4 静态，分级标注）**。
