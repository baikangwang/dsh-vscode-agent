## 一、目标/背景分析

1. **直接动因（用户提问原文）**：「dsh 发布了 0.1.5.alpha.1，本地项目 deepseek-harness 已获新源码，深度调研当前项目有没有需要适配项和优化项，甚至架构改进项。」——需要回答三层：① 我们要不要改（适配项）；② 改了更好的（优化项）；③ 结构性机会（架构改进项）。
2. **最高优先级子问题（沿 0.1.17 报告口径）**：0.1.3-alpha.2 引入的 native runner 隐藏形态弹窗回归（PR #2825，runner spawn 无 windowsHide）在 0.1.5-alpha.1 是否已修——此判定直接决定 `WINDOWSAFE_REGRESSION_MIN_VERSION = '0.1.3-alpha.2'`（src/dshProcess.ts:489）回归阈值的存废：修了则阈值可放宽（须用户评审）；没修则阈值继续有效。
3. **版本号方案面**：用户口述「0.1.5.alpha.1」为点号预发布写法，需核实 registry 实际字符串与上游版本方案是否变更（点号 vs 连字符），并核对扩展 `compareDshVersions` 比较器与 `dshResolver` 匹配逻辑在新版本下的行为。

## 二、范围分析（做什么、不做什么）

**做**：上游检出状态核实（ref/commit 裁定）；npm registry 三重验证（dist-tags + 全列表 + 双写法点查）；发布物 npm pack 解包与产物级哈希对比；alpha.2 → 0.1.5-alpha.1 的 563 提交按集成面切片 diff（闪窗面/版本方案/Web 契约/子进程模型/其他）；对照扩展源码现状做影响评估；产出三类清单与本报告。

## 四、集成面逐项判定（alpha.2 → 0.1.5-alpha.1，563 提交切片）

### 4.1 Windows 控制台/闪窗面（最高优先级）——回归未修（产物级定论）

**判定：PR #2825 引入的隐藏形态弹窗回归在 0.1.5-alpha.1 中未修复。** 三层证据相互印证：

1. **产物级（R1，本轮新增的最重证据）**：已发布 `@deepseek-ai/dsh-subprocess-local@0.1.5-alpha.1` 的 `runner.js`、`runner-launch-COYGu0Dl.js`、`index.js` 与 alpha.2 实机安装树同名文件 **SHA256 完全一致**——扩展实际接触的 npm 发布物里，runner 进程链的字节码与带回归的 alpha.2 没有任何差别。
2. **源码级（R1）**：`git diff e379fa8bdd..HEAD -- packages/subprocess/` 仅 package.json 版本字段与 README 变化，**src 零改动**。HEAD 树中 `windows-job.ts:134-141` 的 runner 启动 spawn 仍为 `{ cwd: process.cwd(), env: runnerEnvironment(…), stdio: runnerStdio(…) }`——**无 windowsHide、无 detached**，与 0.1.17 报告 r2/r3 对 alpha.2 的取证逐字一致；`probeWindowsJob()` 选择链与 koffi 依赖（`koffi ^3.1.0`）原样保留，runner 路径默认生效的条件不变。
3. **修复锚点完整性（R1）**：alpha.1 的三点 windowsHide 修复在 HEAD 仍在——`spawn.ts:319`（taskkill 树杀）、`spawn.ts:659`（spawnSubprocess 主通道 `windowsHide: platform === 'win32'`）、`windows-inspector.ts:150`（taskkillTree）。即：**修复还在，但 ordinary 命令默认改走 runner 后修复被旁路**，与 0.1.17 报告的回归机制完全相同。

**对扩展阈值的影响**：`WINDOWSAFE_REGRESSION_MIN_VERSION = '0.1.3-alpha.2'` **继续有效且归段正确**——`compareDshVersions('0.1.5-alpha.1', '0.1.3-alpha.2')` 在 core `0.1.5 > 0.1.3` 即返回 1 → `judgeWindowSafeByVersion` 划入 regression 区间 → 隐藏形态 WARN 照常触发（src/dshProcess.ts:905-906）。**该警告对 0.1.5-alpha.1 不是误告警，而是正确告警。** WARN 文案中「上游 master 未修」在当前时点仍为字面事实（master HEAD 即 0.1.5-alpha.1 树，未修）；文案未提版本上界，无需改动即保持真值（时代锚点的刷新列为优化项 O-1）。

### 4.2 版本号方案面——无变更，扩展判定链全部安全

1. **比较器（R4）**：`parseSemver`（src/dshProcess.ts:503-512）按标准 semver 解析连字符预发布；`0.1.5-alpha.1` 解析为 `{0,1,5,['alpha','1']}`，与 `0.1.3-alpha.2`、`0.1.2-alpha.2` 的比较在 core 段即分出高下，与预发布标识符规则无关。三个判定点在新版本下行为：`judgeContractByVersion('0.1.5-alpha.1')` → `token`（≥ 0.1.2-alpha.2，authProxy 正常建立）；`judgeWindowSafeByVersion` → `regression`（见 §4.1）。
2. **点号写法风险裁定（R1+R4）**：npm registry 拒绝点号版本（E404 + 全列表无点号），npm 安装的 package.json version 永远是 npm 校验过的合法 semver——**点号写法不可能经 npm 通道进入 `dshResolver` 的匹配输入或 `judgeContractByVersion` 的判定输入**。用户口述的点号写法只是沟通混淆源，不构成代码风险（可选加固见架构改进项 A-3）。
3. **resolver 匹配（R4）**：`dshResolver.ts:454` 的候选匹配是**字符串相等**（`c.version === V`，V 来自 `npm view @deepseek-ai/dsh@<channel> version`，输出经 `/^[\w.+-]+$/` 校验 :375）——registry 返回的版本串与安装目录 package.json 的版本串同源同值，连字符新版本号正常命中；点查 `0.1.5-alpha.1` 已证实 npm view 可返回该串。
4. **dist-tag 语义（R1）**：`alpha → 0.1.5-alpha.1`、`latest/next → 0.1.2-rc.1`——结构与 0.1.17 时点一致（alpha 前移、latest/next 不动）；扩展 `dsh.channel` 的合法值（latest/next/alpha）与归一逻辑（src/extension.ts:48-53）不受影响。alpha 通道用户原地刷新即吃 0.1.5-alpha.1（本机缓存已被更新的实测佐证，见 §零）。
