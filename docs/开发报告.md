## 3. 关键实现

### 3.1 启动路径（runtime.start，对应方案 §6.1）

```
激活(onStartupFinished)
 ├─ 读注册表：dsh 存活（pid 校验 + 端口 __DSH_BOOT__ 双校验）→ 连接 + 登记窗口
 ├─ 探测 3080 外部实例 → 连接 + 接管 pid（netstat 枚举 + 命令行校验）→ 登记
 ├─ 原子启动锁（fs.open 'wx'）：
 │    ├─ 抢到 → 端口预检（非 DSH 占用则回落 0）→ spawn（npx 托管）→ 解析 stdout 端口
 │    │        → 就绪探测 → 写注册表（managedBy=extension）→ 释放锁
 │    └─ 未抢到 → 轮询注册表/端口（≤60s）等 dsh 就绪 → 连接
 └─ 就绪后自动展开右侧边栏（workbench.view.extension.dsh.viewContainer，
     失败回退 toggleAuxiliaryBar）
```

### 3.2 生命周期仲裁（对应方案 §6.3）

- **注册表** `%LOCALAPPDATA%\DshVscode\instance.json`：`{dsh:{pid,port,managedBy,startedAt}, windows:[{app,pid,startedAt}]}`，原子写（tmp+rename）。
- **关停判定**（`process.on('exit')` 同步钩子，因 deactivate 在窗口关闭时不保证调用）：
  注销本窗口 → 计数为空 → dsh.pid 存活 + netstat 确认仍监听注册表端口（防 pid 复用误杀）→ `taskkill /T /F`。
- **外部实例**：连接时即接管 pid（`netstat -ano` 解析 + PowerShell CIM 命令行校验含 dsh 特征），
  与托管实例一样在最后窗口退出时关停（用户决策）。

### 3.3 运行时托管（对应方案 §6.4）

- 首次/升级：`cmd /c npx --yes --prefer-offline @deepseek-ai/dsh@<channel> web --host 127.0.0.1 --port <port> --no-open`；
- 端口解析正则 `dsh web:\s+(http://127.0.0.1:(\d+))`（与 dsh-desktop 同一契约）；
- 崩溃退避重启 1→2→4→8→16→32s，上限 6 次转 error；`dsh.command` 支持自定义启动命令。

### 3.4 面板（对应方案 §3.2）

- `viewsContainers.auxiliarybar` + webview 视图 + `registerWebviewViewProvider`；
- CSP：`frame-src http://127.0.0.1:*`；iframe `sandbox="allow-scripts allow-forms allow-same-origin allow-downloads"`（官方 simple-browser 范式，同源 HTTP/WS 全可用）；
- 状态覆盖层（starting/ready/error）+ 工具栏（打开浏览器/重启/停止）+ 状态栏项。

## 9. GUI 联调发现与 0.1.1 修复（2026-08-24，v1.1）

> 触发：按《联调测试剧本 v1》执行场景 A（外部 3080 实例接管）。联调暴露 3 个 bug，
> 均已定位根因并在 `0.1.1` 修复。VSCode 实测版本 **1.134.0**（本机 `AppData\Local\Programs\Microsoft VS Code`）。

### 9.1 Bug A：右侧边栏无 DSH 容器，面板落到左侧活动栏（主 bug）

**现象**：右侧边栏（auxiliary/secondary sidebar）为空（仅 "Drag a view here"），DSH 视图出现在左侧活动栏底部，且卡 `initializing`。

**根因（双重，均在 VSCode 1.134 workbench 源码实证）**：
1. **容器 id 含点号**：`dsh.viewContainer` 不满足容器 id 正则 `^[a-z0-9_-]+$`，`isValidViewsContainer` 校验失败 → `viewsContainers` 贡献被整体拒绝。用户扩展宿主日志中的
   `ERR … property 'id' is mandatory … Only alphanumeric characters, '_', and '-' are allowed` 即此错误。容器从未注册，`dsh.panel` 视图因找不到所属容器被移到默认（主侧栏）容器。
2. **location key 改名**：1.134 中 `viewsContainers` 的合法 key 为 `activitybar` / `panel` / `secondarySidebar`（`additionalProperties: false`）。旧 key `auxiliarybar` 被静默丢弃（UI 上 auxiliary bar 已更名 secondary sidebar）。

**修复**：容器 id 改为 `dsh-viewContainer`（无点号）；location key 改为 `secondarySidebar`；`openPanel()` 命令改为 `workbench.view.extension.dsh-viewContainer`（1.134 对自定义容器自动注册 `workbench.view.extension.<containerId>` 打开命令）。`engines.vscode` 提升至 `^1.134.0`。

### 9.2 Bug B：外部实例 pid 恒为 null → 最后窗口不关停 dsh

**现象**：场景 A 关闭最后窗口后，外部 dsh（21160）未被杀，注册表 `dsh.pid: null`、`windows: []`。

**根因（代码 bug，非环境）**：`runtime.writeRegistry()` 旧实现仅持久化 `this.process?.pid`（**托管 spawn** 的子进程 pid）。外部**接管**路径不 spawn 进程，`this.process` 恒为 null → 注册表永远写入 `pid: null`。随后 `shutdownBookkeeping` 见 `pid === null` 走安全侧不杀 → 外部 dsh 存活。用户实测：普通终端用同一份 `out/instance.js` 能正确解析 `resolvePortPid(3080)={pid:21160}` 与命令行，证明判定链本身可用，问题只在"接管到的 pid 没被存下来"。

**修复**：新增 `adoptedPid` 字段，`adopt()` 记录接管到的 pid，`writeRegistry()` 用 `this.process?.pid ?? this.adoptedPid ?? null` 持久化。另增强健壮性：CIM 取命令行预算 10s→15s（冷 WMI 启动慢）；CIM 不可用时回退到"端口页签名（`__DSH_BOOT__`）已验证"直接记录 holder pid——**不削弱防误杀**，因最后窗口关停前仍有 pid+port+页签名三重复查。

### 9.3 Bug C：面板渲染（原观测项，现已确认根因并在 0.1.2 修复）

**现象（0.1.1 复测确认）**：右侧边栏正确出现 DSH 面板（Bug A 已修复生效），注册表 `dsh.pid: 21160` 非 null（Bug B 已修复生效），但面板**无样式、overlay 停留在 `initializing…`**：
- 第一行 `initializing…` + 三个按钮；第二行 `initializing…`；下方一个空白的"文本框"（即未应用 `display:none` 的空 iframe）。
- 扩展宿主日志：`Applying inline style violates … style-src 'self' https://*.vscode-cdn.net` + `Uncaught SyntaxError: Failed to execute 'write' on 'Document': Invalid or unexpected token`（`…purpose=webviewView:1064`，对应 `contentDocument.write(newDocument)`）。

**根因（0.1.2 确认，源自 VSCode 1.134 `toContentHtml` 源码）**：本扩展 webview 的**严格 CSP** 与 VSCode 注入机制冲突。`toContentHtml(data)`（`pre/index.html:847`）会向扩展 HTML 注入两样**无 nonce** 的节点：
1. `_defaultStyles`（`<style>`，第 875 行）→ 被我们的 `style-src ${cspSource}` 拦截 → 面板**全部样式失效**（含 iframe `display:none`、overlay 定位等）；
2. `_vscodeApiScript`（`<script>`，第 871 行）→ 被我们的 `script-src 'nonce-${n}'` 拦截 → `acquireVsCodeApi` 未定义 / 内联脚本的状态监听建立失败 → overlay 停留在初始 `initializing…`。

面板 HTML 本体能被写入并解析（故看到工具栏/按钮/空框），但注入的样式与 API 脚本被 CSP 挡掉，是"有面板却卡 initializing 且无样式"的确切解释。`document.write` 的写入链报错与该阻塞同源。

**修复（0.1.2）**：webview CSP 改用 `style-src 'unsafe-inline'; script-src 'unsafe-inline'`（保留 `frame-src http://127.0.0.1:*`），放行 VSCode 注入的默认样式与 API 脚本及本扩展内联脚本。仅内嵌本地 127.0.0.1 的 dsh UI，安全权衡可接受。移除不再需要的 `nonce()` 与 `${csp}` 引用。

## 10. 0.1.3 修复：面板卡 Initializing（webview 启动竞态，2026-08-27）

### 现象补充
用户手动在 cmd 启动 `npx @deepseek-ai/dsh web` 后再开 VSCode：状态栏 `● DSH 3080`（runtime ready），
但面板停留在初始 `initializing…`。非 Bug C（CSP）复发——0.1.2 已放行 `acquireVsCodeApi`；而是**消息竞态**。

### 根因（详见 `docs/archive/面板卡Initializing根因分析.md`）
扩展在 webview 页面尚未挂上 `message` 监听器时（`onView:dsh.panel` 解析早于 runtime ready 约 8s）就 `postMessage`，
消息全部丢失；而扩展只在 **state 变化**时重发，ready 后无变化 → `ready`/`setUrl` 永不补发 → 面板永久停在 `initializing…`。
纯 `initializing…`（非 `正在启动 dsh…`、非 `Webview API 不可用` 诊断）证明确为「消息未送达」。

### 修复（`src/webview.ts`，commit e00f974，分支 `fix-webview-boot-race`）
- **握手（核心）**：webview 端监听器/按钮全注册后补发 `vscode.postMessage({type:'webviewReady'})`；
  扩展侧 `onDidReceiveMessage` 收到即 `refresh()` 无条件重发当前 state 快照（`state:ready` 分支会 `setUrl`）→ 无论何时 boot 完成都会拿到 URL。
- **dispose 置空**：`onDidDispose` 中 `if(this.view===webviewView){this.view=null;this.lastUrl=null}`，避免对已回收 webview 投递、重建后 setUrl 不被 lastUrl 抑制。
- **类型收敛**：`WebviewMessage` 类型别名。
- 附带：带入了本会话前工作树遗留的 0.1.2 Bug C CSP 修复（`nonce→unsafe-inline`+acquireVsCodeApi 诊断）——非本次新增，QA 已证实与已装 0.1.2 逐字一致且必须保留。

### 发布配套
- `package.json` version → **0.1.3**；`.vscodeignore` 补 **`.dsh/**`**（原缺失致首轮打包把 `.dsh/` 打进去；修复后 12 文件 / 21.77 KB）。
- 产物 `dsh-vscode-agent-0.1.3.vsix`（SHA256 `09B827B6A05B23FC21E37670E2CB0537F5029FA3F451AFD5F9B705892CE2A883`）。
- 验证：`tsc` 0 错误；`node scripts/sim.mjs` **8/8 PASS**（full-access 解除沙箱 netstat EPERM，纯 Node 层没有回归）；QA 代码检查 C1-C6 PASS、发布检查 P1-P4 PASS。

### 复测（用户执行）
1. 卸载 0.1.2 并**完全退出 VSCode**；`code --install-extension .\dsh-vscode-agent-0.1.3.vsix`。
2. Windows cmd 手动 `npx @deepseek-ai/dsh web` → 再开 VSCode。预期：右侧边栏**直接显示 dsh UI**、不再卡 `initializing`；状态栏 `● DSH 3080`；注册表 `dsh.pid` 非 null。

## 11. 0.1.4 修复：面板卡 Initializing（webview 消息层自愈，v3，2026-08-27）

> 承接 0.1.3（webview 启动竞态修复第一阶段）。v3 把 webview 消息层从「一锤子握手」升级为
> **带 ack 的自愈状态机** + 全程观测日志，覆盖握手已发生但仍可能出现的丢消息/丢 ack/空 view 场景，
> 是 fix-webview-boot-race 修复线的完整实现（含同分支既有的 runtime/instance/dshProcess/paths/extension 改动）。

### 现象与目标
0.1.3 已通过 `webviewReady` 握手在 boot 竞态下补推快照，但**事后仍可能有缺口**：
消息投递后若 ack 丢失、页面渲染了过期快照、或 push 落在 view 已被 dispose 的窗口，面板仍可能停在 `initializing…` 且无观测痕迹。v3 目标是让该链路**可自愈 + 可取证**。

### 核心修复（`src/webview.ts`，v3）
- **webviewReady + stateAck 带 ack 的自愈状态机**：页面端对每次 `state` 快照回 `stateAck { appliedState }`；

## 12. 0.1.5 修复：面板卡 Initializing（webview iframe 启动时直接写入最终地址，v4，2026-08-27）

> 承接 0.1.4（webview 消息层 v3 自愈）。0.1.4 已带 v3 ack 修复但仍真机卡 `initializing`，
> v4 放弃「依赖消息/脚本驱动面板显示」的假设，改为 **iframe `src` 在页面 HTML 渲染时即写入最终值 `runtime.url`**，
> 使 dsh UI 不依赖任何消息与页面脚本即可直接显示——直击 0-handshake 根因。

### 现象与根因
0.1.4 的 v3 依赖 `emit → recv webviewReady → ack` 消息往返把 URL 推给面板；若该链路任一环丢失（ack 丢失、
页面脚本未执行、view 与 dispose 竞态），面板仍可能停在 `initializing…`。v4 把「显示 dsh UI」从
「消息驱动的增强行为」下沉为「HTML 本体自带的默认行为」，从架构上消除对该链路的主依赖。

### 核心修复（`src/webview.ts`，v4）
- **iframe src 启动即写入最终值 `runtime.url`**：`html()` 在生成面板 HTML 时就把 `src="${runtime.url}"` 写入
  iframe（`style="display:block" src=…`），页面一旦渲染即加载 dsh UI，**不依赖消息/脚本**即可显示（0-handshake 根因）。
- **面板直接显示 dsh UI**：`frameAttr` 在 `known`（runtime 已就绪）时直接内联 `display:block` + `src=url`；
  页面脚本降为**增强层**（订阅状态/回 ack/工具栏联动），不再承担「决定是否显示」的主责。
- **boot 观测**：页面加载即在 `document.title` 追加 `.booted`、`console.log('[dsh-panel] page booted at', location.href)`，
  并在 DOM 状态元素写 `page booted…`——用于取证区分「脚本未执行但仍显示 dsh UI」与「文档未渲染」。
- **`bakedUrl` 单次重设**：仅当 `runtime.url` 变化且不等于已写入的值时用 `panelLog('re-bake html url=…')`
  重新生成一次，避免就绪后重复 rewrite HTML 覆盖用户已交互的页面。
- **去硬编码硬约束**：C3 专项已核对无硬编码端口/路径/文案残留（QA 前置轮已确认，非本次新增）。

### 15.2 P-IDENT 实现要点（G1-G4 + T2）

- **G1 自保守卫**（instance.ts `scrubWindowsWithIdentitySync`）：单点守卫 `isSelf(pid)` 同时覆盖 liveness 遍与 identity 遍——self 条目直接保留、永不进入 `dead[]`/`foreign[]`/`removedPids`；手术式重写层按 `removedPids` 过滤 → 两条写路径均被单点守卫覆盖；接线：T1b 与 T2 均传 `selfPid: this.options.windowPid`，`registerWindow` 不做身份校验（本窗登记无需自证）。
- **G2 正证据反转**（判定层）：`foreign` 重定义为正证据清除档——**CommandLine 非空且无签名命中 + ExecutablePath 非空 + basename(ExecutablePath) ∉ VSCODE_EXE_FAMILY**（basename 忽略大小写，`split(/[\\/])/` 取尾段，不依赖 path.win32/posix 差异）；判定顺序 = CommandLine 空→unknown → 签名命中→exthost → 三条件齐→foreign → 其余一律 unknown（含 H2a 落点：家族 exe + 签名未命中）；签名清单降级为 exthost 正判定档（保留/翻转基线/诊断），不再是清除把关；pid 复用清理能力不回退（无关进程 exe 非家族 → foreign → 照清）。
- **G3 查询硬化**（`queryIdentitySync`）：`IDENTITY_QUERY_SCRIPT` 编译期常量（`-Filter ProcessId=$env:DSH_IDENTITY_PID` 无引号无空格 WQL 裸 token + 单查询三字段 `Name, ExecutablePath, CommandLine`）；pid 只经 `env: { ...process.env, DSH_IDENTITY_PID: String(pid) }` 进入，`-Command` 载荷零双引号、零插值；`spawnFn` 注入扩展点（默认 `spawnSync`）供 sim 无头断言；env 缺失防御路径 status≠0 → unknown（V3b）。
- **G4 翻转守卫 + 60s 宽限**：翻转守卫只在**新鲜查询路径**（未过期缓存命中维持短路原样——直接返回、无比对、零 spawn）；比对对象 = **上一条缓存判定（无论是否过期）**：foreign + 上一条 exthost → 返回 unknown + `appendDecisionLog('identity flip exthost→foreign for pid <pid>; downgraded to unknown')` + 缓存条目写 unknown → 隔轮仍 foreign 照常清除（`identityCache` 模块级 Map 语义不变：TTL 只判新鲜度不删条目，过期条目 verdict 参与翻转比对）；宽限期 `IDENTITY_GRACE_MS=60_000`（`nowMs` 注入扩展点，缺省 `Date.now()`）：`startedAt` 距 now < 宽限 → 豁免**身份**清除；liveness 死亡条目照清不受影响。
- **T2 幂等短路**（runtime.ts）：`shutdownDone`/`shutdownResult` 两字段——首调完整簿记（unregister → T2 scrub（含 selfPid 防御传参）→ 三重检查裁决）并落结果；extension.ts 三处 exit 钩子（`process.on('exit')` / dispose / deactivate）第 2/3 次调用 → `rlog idempotent skip` + 返回首调结果，**零 CIM 查询、零注册表写**；`start()` 入口重置两字段（同进程禁用→重激活按附着纪元重簿记）。

### 15.3 P-POPUP 方案 B 实现（consoleVisible，默认 true）

- 唯一翻转点 = `dshProcess.ts` spawn 选项 `windowsHide: !consoleVisible`；`detached:true` / `stdio:['ignore',fd,fd]` / `unref()` **逐位不变**（PP-1 双态断言 + unref 计数）。
- 传递链：extension.ts `c.get('consoleVisible', true)` → `DshRuntime` options → `launchManaged` → `DshProcess` options（纯 Node 层零 vscode import，分层红线不破坏）。
- custom `dsh.command` 路径不受该配置语义影响（cmd/npx 链遗留边界照旧；PP-1 以 `buildLaunch('')` 直断 argv 形态回归）。
- **默认值 = true（用户评审裁决 2026-08-29）**：开箱即消除运行期工具调用弹窗，代价为常驻一个 dsh 控制台窗（用户已知悉）；dsh 上游统一 windowsHide 修复落地后可切回 false 达成「无常驻窗口 + 零弹窗」终态（设计文档 ADR-20/§4.5 已由架构师 v2.5 文档微修订同步）。

## 17. 0.1.18 修复轮：P1 runtime error 事件监听 + dispose 复核（2026-09-09，开发专家）

> 依据《0.1.18问题分析-sim无头回归脚本非确定性崩溃根因与修复方案》（commit 5bfb252）§5.2 与 §十一 任务 7/8（根因方案 v1.1，QA 设计审计 7/7 通过、用户评审批准）。sim 侧修复（F1–F5，`scripts/sim.mjs`）由测试专家并行实施，本节不涉及。

### 17.1 P1（任务 7）：extension.ts 为 DshRuntime 挂 error 事件监听

- **缺陷事实**：`src/extension.ts` 此前没有监听 DshRuntime 的 error 事件。runtime 的 4 处 `emit('error')`（runtime.ts L496 / L585 / L872 / L1116，逐一核实）在无监听者时会被 Node EventEmitter 重新抛出，扩展宿主在「detached 启动重试耗尽 / adopt 会话不可用 / probe 会话失效 / step4 等待超时」场景下可能被拖垮。
- **改动**（`src/extension.ts`，紧跟既有 `runtime.on('state', updateStatus)` 之后、启动路径之前挂载）：`runtime.on('error', (msg: string) => { appendDecisionLog(`[extension] runtime error: ${msg}`); updateStatus() })`。监听器只做两件事——日志留痕（走既有 `appendDecisionLog` 通道，payload 原文转发、不臆造字段）与幂等重刷状态栏 error 态（既有 `case 'error'` 分支：`statusLine('error')` + tooltip 取 `runtime.errorMessage`）。
- **职责边界（按 §5.2）**：不做额外重启（重试预算已在 launchManaged 内收敛）；不做全局弹窗。面板与详情视图的 error 态渲染由既有 `state` 订阅链路完成（4 处 emit 前均已先 `setState('error')`，`emit('state')` 先行驱动 webview.ts L66 / webviewDetails.ts L57 的刷新），监听器职责仅是兜底防 crash 与日志留痕。

### 17.2 任务 8：dispose() 的 removeAllListeners() 语义复核（§5.2 评审项，文档层确认）

- **dispose 实现**（runtime.ts L1349-1353）= `stopProbe()`（清探测定时器）+ `stopProxy()`（停本地反代）+ `removeAllListeners()`；**不重置** `state`、**不取消**飞行中的异步调用。调用点只有 extension.ts 的订阅 dispose 回调（扩展停用/窗口重载时；`process.on('exit')` 与 `deactivate()` 只调 `shutdownBookkeeping()`，进程退出时事件循环终止、飞行中 promise 不再执行，无残余窗口）。
- **逐处 emit 可达性（dispose 之后）**：①L496（step4 等待超时）——理论可达（start 飞行中停用扩展，等待窗口最长 60s）；②L585（启动重试耗尽）——理论可达且窗口最长（6 次重试 + 退避总时长可达数分钟）；③L872（adopt 会话不可用）——理论可达（adopt 在 start 流程内；probeTick 401 分流路径 dispose 后仅剩飞行中的一次 tick）；④L1116（会话失效）——理论可达（同 ③，dispose 不重置 state，守卫 `state === 'ready'` 仍通过）。
- **结论**：dispose 后**不存在定时器驱动的新触发**（stopProbe 清掉 interval，探测类 emit 的常规触发面闭合）；但 `removeAllListeners()` 会把 P1 的 error 监听一并移除，若停用扩展恰逢 start()/launchManaged()/单次 probeTick 飞行中且此后恰走到 4 处 emit 之一，将回到「无监听者 emit('error') 抛异常」的路径（async 链上表现为无 catch 的 promise rejection）。触发前提苛刻（停用扩展恰逢启动/重试/探测飞行），正常生命周期内 P1 监听覆盖全部 4 处。按 §5.2 评审项本轮只做文档层复核、不改 runtime.ts（§十二：不改 src/ 启动/接管/仲裁逻辑）；残余窗口的候选闭合方向（未实施，记录备查）：dispose 时置终态 / emit 前判 `listenerCount('error')` / dispose 后保留最小 error 监听。
